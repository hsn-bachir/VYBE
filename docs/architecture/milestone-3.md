# M3 architecture — administrator invitations and password management implemented, later slices proposed

## M3.1C implementation (2026-11-04)

Core adds active administrator account creation and resend plus public invitation acceptance. A new account is an active ordinary user with unverified email, `invitation_pending=true` and a random unusable password hash. A purpose-separated invitation table stores one email-bound SHA-256 token digest per user with configurable 60-minute expiry. Admin creation and resend lock active administrator rows in ID order, recheck the actor, then lock the target where applicable. Account/token issuance and `user.created` or `user.invitation_resent` audit commit together before synchronous mail dispatch. Transport failure leaves a pending invitation for explicit resend; `accepted` reports transport acceptance only. The log mailer is blocked from handling token-bearing messages. Acceptance locks user then token, rechecks eligibility and email, sets the password and verification time and deletes the token atomically without signing in. Editing an invited email deletes the old token. React adds create/resend controls and an account setup route. Hard deletion, reporting/moderation and recommendations remain outside this slice.

### M3.1C administrator password management (2026-11-05)

Core extends the M3.1C administrator account flow with direct password change and broker-based reset initiation. Only a verified active administrator may start either action; the service locks and rechecks the actor and target, excludes self, other administrators and invitation-pending accounts, and writes an allowlisted audit action in the same transaction as the credential or token change. Direct change requires the actor's own current password and uses the shared registration password rule. Laravel's existing `password_reset_tokens` table and broker provide a separate one-use, expiring reset flow; invitation tokens remain independent. The browser receives no password or reset token. A password-free change notice and token-bearing reset notice are dispatched only after commit, with safe delivery-failure behavior.

Direct change and completed reset rotate a private session version and remember token. Core deletes database sessions in the transaction when the configured session store shares the Core connection. Live middleware compares the private version on each authenticated request, so file-backed sessions from before a password change lose access on their next request. The same five-field `/auth/me` projection remains intact. React adds a Password Management section to the existing admin detail screen and a lazy `/password/reset` form under the current auth layout. Catalog, reports and recommendations are unaffected.

## M3.1B implementation (2026-11-04)

Core now exposes verified administrator-only user listing, detail, account identity editing, moderator role changes, and account status transitions. The `administrative_actions` table records allowlisted changes atomically with user updates. Mutations lock active administrator rows through the `(account_status, role, id)` index in ID order, then lock the target and recheck actor permissions and last verified active administrator protection. Database-backed sessions on the Core connection are revoked in the same transaction; fresh M3.1A state checks remain authoritative for other session stores. An administrator changing their own email is signed out and must verify the replacement address; the last verified active administrator cannot change email. No user creation, hard deletion, reports or recommendation logic is added. React adds lazy `/admin/users` and `/admin/users/:id` screens under the existing access guard, with a further administrator-only guard, real paginated search/filter, server-confirmed actions and responsive dialogs. M3.2 and M3.3 remain pending.

## M3.1A implementation (2026-11-03)

M3.1A added role and account status to users. Protected Core API routes read the current user row on every request; banned and deactivated sessions receive safe 403 responses, with logout still available. Restricted accounts retain library and profile access and may delete their own review, while rating writes and review creation/edits are denied. Write services lock the user row and recheck status inside database transactions after any Catalog call. Laravel gates and `EnsureRole` support administrator and future moderator routes. `GET /api/v1/me/access` is the private role/status projection; `/auth/me` remains unchanged. An existing verified active user can be promoted once through `app:provision-admin {user_id}` on the Core server. The React `/admin` route provides role-gated administration or moderation landing states. M3.1B is described above; M3.2 and M3.3 remain pending. The M3.0 plan below remains the proposal for those later slices.

## Ownership and flows

```text
Browser React --cookie + XSRF--> Core API --service token--> Catalog API --> TMDB
                                 |                         |
                              vybe_core                vybe_movies/cache
```

Core alone owns users, roles, account state, review visibility, reports, action history, personal signals, scoring, and browser-facing APIs. Catalog alone owns TMDB access, candidate sourcing, normalized movie metadata and its caches. React calls only Core. Keep one SPA, two Laravel applications and their existing databases; no cross-database joins, recommendation service, ML model, moderation vendor or permissions package.

M3.1 first adds server-side role/state checks to all protected Core routes, then admin account operations and their UI. M3.2 adds review reports and moderation while preserving the existing review URLs/owner writes. M3.3 adds one bounded Catalog candidate contract, a Core ranker, and a Home section. Each new internal route requires the existing `catalog.internal` token; it conveys service identity, never a user's role.

## Roles and account state

Persist one `users.role` value (`user`, `moderator`, `admin`) and one `users.account_status` value (`active`, `restricted`, `banned`, `deactivated`). A restricted account can read and use personal library/profile but cannot create or edit reviews, submit reports, or rate movies; existing review deletion remains available. This is the M3 community-write restriction. A banned or deactivated account cannot use authenticated routes. Public movie discovery remains available without a session. A deactivated account is reversible by an admin; a hard delete is a separate, irreversible operation.

| Capability | User | Moderator | Admin |
| --- | :---: | :---: | :---: |
| Personal library/profile and read community | ✓ | ✓ | ✓ |
| Rate, create/edit review, report (active only) | ✓ | ✓ | ✓ |
| Delete own review (including restricted) | ✓ | ✓ | ✓ |
| View/resolve reports; hide/restore/mark spoiler | — | ✓ | ✓ |
| List/create/edit users; change status; hard delete | — | — | ✓ |
| Assign/revoke moderator | — | — | ✓ |
| Grant admin | — | — | Trusted server-side provisioning only |

Use a small role/status enum or constants, Laravel policies/gates for individual actions, and middleware for authenticated, verified, non-banned/non-deactivated access. New admin routes require `auth:sanctum`, `EnsureVerifiedAccount`, account-state check and role gate; authorization repeats at object/action level. Existing Core route groups must also receive state checks in M3.1, including `/auth/me` and review writes; a new gate only on `/admin/*` would leave banned sessions active elsewhere. Admin self-demotion, self-ban/deactivation/delete, and removing the last active admin are rejected under a user-row lock/transaction. Only a trusted CLI command or deployment seeder with explicit operator inputs can bootstrap the first admin; registration and public/profile PATCH never accept role/status. Subsequent admin promotion is also server-side only in this phase; API role updates may assign `user`/`moderator` but never `admin`.

After status/role changes, revoke database sessions and Sanctum tokens for the target where supported, clear the current session when the target is the caller, and check fresh account state/role on every protected request. Do not cache permission decisions in session or React. Each protected write must re-read and lock the actor's user row inside its transaction before changing data; a ban/demotion takes the same lock, so a write ordered after the committed restriction is rejected even if its request started earlier. Lock actor and affected users in a consistent ID order and retry expected deadlocks. Production must use a centrally revocable session driver; the checked-in `.env.example` uses `SESSION_DRIVER=database`, while CI uses array sessions for isolated tests. Password/verification changes invalidate affected sessions. Login failure for banned/deactivated accounts uses the same generic credential response; `/auth/me` may return a safe account-status 403 after an existing session is identified. Audit both revocation and the next-request denial in tests.

Admin creation reuses username/email validation and a dedicated `account_invitations` token table and uses the implemented M3.1C invitation/password-setup endpoint and UI: create an unverified `user` with a non-usable random password hash and invitation marker, then email a short-lived one-use setup link after commit. The recipient sets a password and verifies email. Do not return or email plaintext passwords. If delivery fails, preserve the unverified account, report delivery as pending and offer a throttled resend; never claim delivery succeeded or send within a transaction that might roll back. Admin edits are limited to username and email (email change clears verification and revokes sessions); profile bio/avatar remain owner-managed. Hard delete cascades Core-owned library, ratings, reviews and collection rows; report/history references become null or retain only non-PII IDs as defined in the schema. No Catalog rows are deleted. Confirm deletion in UI. Legal retention/erasure policy and deployment mail readiness require owner sign-off before M3.1 hard delete ships.

## Moderation and reporting

Reviews remain immediately public on creation. Reports never automatically hide content or sanction accounts. A reporter may file one report per review; a second attempt returns the existing report without creating another. Public reviews exclude hidden rows, including counts and pagination; owner GET returns the hidden review with a visibility indicator so the owner knows its state. Hidden body remains accessible only to its author and moderators through protected endpoints. Reporting a hidden/deleted review returns the same safe 404 as a missing target; report detail/history is private to moderators/admins. A deleted target leaves a report with `target_available=false`, which can be dismissed and audited; never reuse a numeric target ID across types.

The existing author flag stays `reviews.contains_spoilers`; add `reviews.moderator_spoiler` and compute public `contains_spoilers = author_flag OR moderator_flag`. Author PATCH can change only its own flag and body; it cannot clear moderator enforcement. Moderator unmark clears only the moderator flag. A hide action sets `visibility=hidden`, preserving the row and its owner, and records actor/reason in the action log. Restore returns it to `visible` without changing spoiler flags. Review deletion remains an owner action; it removes the row and its public presence while report/history metadata survives per retention policy. Moderator powers never confer arbitrary owner edit/delete rights. All moderation actions lock the target row and write its state, report resolution where relevant, and immutable action log in one Core transaction; repeated desired-state actions have a documented no-op response and do not duplicate log rows. Concurrent author edits cannot clear moderator flags; concurrent delete yields a safe 404/target-unavailable outcome.

Use a `reports` target kind allowlist with only `review` enabled now. This leaves a schema path to other kinds without accepting PHP class names or implementing their APIs. Validate target existence/visibility in a transaction, store `reporter_id` from the session, limit reason/description, enforce uniqueness and per-user/IP throttles. Resolve to `resolved` when moderation action addresses the report; dismiss to `dismissed` with a reason. Reports are visible only to the reporter via create response and to moderators/admins via the queue. No public report listing. The single `administrative_actions` table records both account and moderation decisions, without review body, password, email or full request payload.

## For You recommendation design

M3.3 is deterministic content matching, not an AI service. Read at most the 50 most recent rows from each of ratings, watchlist, watched and collection memberships, using stable timestamp/ID order; union, deduplicate by TMDB ID and retain at most 50 most recent distinct IDs. Then use bounded indexed queries for those IDs to retrieve their actual rating, watchlist/watched membership and collection count, including older overlapping rows; cap the collection contribution. Aggregate overlaps: latest rating has strongest influence (`5:+4, 4:+2, 3:0, 2:-2, 1:-4`), collection membership adds `+1` capped at `+2` per movie, watchlist `+1`, watched without a rating `+0.25`. If rating is 1 or 2, clamp the combined seed weight to at most zero so collection/watchlist membership cannot turn dislike positive; cap all weights to `[-4,+6]`. Rank seeds by absolute signal, then recency and ID. A watched movie is excluded from results regardless of rating. Collection names have no semantic meaning.

Use at most the five highest-ranked seeds for detail features, and at most three of those for experience credits; missing or unavailable features are omitted. For each known seed/candidate feature, use normalized genre IDs; use director/cast IDs only when already available in Catalog's bounded experience cache, and writers only after the Catalog normalizer explicitly supports them. Do not request full credits for dozens of candidates. For feature type `t`, affinity `A_t(x) = clamp(sum(seed_weight for seeds containing x) / max(1, sum(abs(seed_weight) for feature-bearing seeds)), -1, 1)`. Score a candidate on a 0–100 scale from `50 + 30*mean(top 3 genre affinities) + 12*max director affinity + 5*max writer affinity + 3*mean(top 3 cast affinities) + quality`, clamped 0–100. For each feature type, include only actual matched affinities, sorted by absolute magnitude then ID; mean the first three where specified, and use zero for an absent type. This lets negative-only matches reduce the score. `quality` is a bounded `[-3,+3]` adjustment using Catalog TMDB rating only when vote count meets a configured floor; it cannot dominate personal signals. These are configurable starting values, not measured optimum. A candidate with no known positive matching feature is not labelled personalized.

Take at most 60 candidate IDs from a new bounded Catalog contract, merge/deduplicate by ID, exclude watched and all already-rated movies (including disliked titles) with bounded indexed `WHERE IN` checks against the full owner history, not only the 50 seed sample, then rank by score DESC, Catalog candidate order ASC, TMDB ID ASC. Watchlisted titles may remain so users can rediscover them. A personalized response includes only candidates with a positive supported match and may contain fewer than 12. Apply the same watched/rated exclusion to popular fallback. Return at most 12 per request; at most two titles with the same strongest genre in each six-item window when alternatives exist, using a deterministic stable pass. Explanations derive only from positive matched features and a contributing positive seed: e.g. `Because you enjoyed science fiction`, `From a director in movies you rated highly`, or `Inspired by movies in your collections`. No explanation when evidence is absent. Never infer preference from a title or collection name.

Current contracts cannot do this efficiently: summaries lack genres, experience gives only a few cached people/related per ID, and there is no genre-based candidate API. M3.3 therefore owns one additive internal `POST /api/internal/v1/movies/recommendation-candidates` contract with `genre_ids` (1–3 positive IDs), `seed_tmdb_ids` (0–5), and `limit` (1–60). Catalog uses cached/provider-ranked bounded discovery from those genres plus cached related IDs; it returns up to 60 existing eight-field summaries with `genre_ids` and optional **cache-only** `director_ids`, `cast_ids`, `writer_ids` (empty when unavailable). Catalog may add minimal normalization/cache of genre IDs from list results and writers from existing appended credits; it must not introduce per-candidate detail calls. Core obtains seed genres from at most five existing detail calls only when needed (cache/stale allowed); seed creatives from at most three existing experience calls. Core never calls TMDB. Validate all returned IDs, lengths and types in the Core client. The new Catalog endpoint is a proposal, not present now, and must be implemented/tested before Core consumes it.

This first version intentionally allows genre-based recommendations when creative metadata is missing; explanations mention creatives only on actual matches. M3.3 should measure coverage in fixtures and a real Catalog smoke check. If the endpoint cannot source a useful genre pool within the provider budget, fall back to ordinary popular results and label the section `Popular to explore`, never `For You` or personalized. Cold start (no positive feature-bearing signal) also uses existing popular discovery with an explicit fallback mode. During a Catalog outage, serve a short-lived previously computed per-user result only if its source revision is unchanged, marked `stale`; otherwise return safe 503 and let the Home popular feed continue. Cache private results for about 10 minutes under user ID plus the database `recommendation_revision`; increment it in the same transaction as every relevant write. Read revision before and after computation and publish only if unchanged, so an in-flight old result cannot become current. No permanent recommendation table. Cap at five seed detail calls, three seed experience calls, one candidate request, at most one optional batch summary request of no more than 50 IDs, and at most one popular fallback request per fresh computation; the candidate DTO already includes summaries. Candidate retrieval may use at most two provider discovery page fetches (existing retry policy still limits attempts per fetch). Impose an overall eight-second Core computation deadline with per-call timeouts bounded by the remaining budget and at most three concurrent seed calls; use available partial features or the explicit fallback on expiry. Do not hold a DB transaction during HTTP. Avoid per-candidate calls. Cache locks prevent duplicate computation. Record latency/call counts in M3.3 tests and revise only from evidence.

## Security and rollout boundaries

Validate IDs, enums and strict JSON bodies in Form Requests; use owner-scoped/policy queries, safe 404 for unavailable/non-owned targets, no-store on private/admin results, narrow admin Resources, and no secrets or password hashes in responses/logs. Use existing Sanctum session/CSRF stack even when `Origin` is absent. Add dedicated throttles for admin reads/writes, reports and recommendations; report submission is limited by both account and IP. Re-check authorization inside state-changing transactions and serialize last-admin/status changes. Public review filtering must be applied in the query, not in React. Moderator actions cannot bypass owner-only review API. Test 401/403/404/409/419/422/429, access with a retained session after ban/demotion, cross-user IDs, duplicate report races and Catalog failures.

For administrator takeover risk, require HTTPS, secure cookies, strong existing password rules, login throttles and tightly controlled server provisioning; monitor action history and limit production administrator accounts. The checked-out app has no MFA. Decide whether to require an external identity-aware access layer or add MFA before internet-facing administration; neither is claimed as implemented here. Avoid returning user search details to non-admins and do not put invitation tokens in server access logs or referrer headers.

Release order: M3.1 schema and default-user backfill → state checks and admin API/UI → M3.2 schema/API/UI → Catalog candidate contract → Core ranking/API → React Home. Deploy Catalog contract before the Core consumer. Keep M2 release/CI acceptance tracked separately; this architecture document does not assert it passed.
