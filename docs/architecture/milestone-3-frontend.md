# M3 frontend integration — moderation screens implemented; recommendations proposed

## M3.2 current implementation

Movie Details reuses `ReviewCard`, `Dialog`, the shared Axios client and auth/access hooks to offer Report on another author's visible review only to a verified active account. The dialog explains that submitting a report does not remove content, validates a reason and optional 1000-character description, keeps input after a failed request, and distinguishes new from duplicate server-confirmed reports. Owner editing initializes from `author_contains_spoilers`, so a moderator-enforced flag is not copied into the author's own toggle. A hidden owner review is labelled clearly in the personal panel.

The existing admin shell now links Reports, Reviews and History for moderators and administrators; Users remains administrator-only. `/admin/reports` has status filters, pagination and missing-target indicators. `/admin/reports/:id` shows the safe reporter/review projection and reason-confirmed resolve or dismiss actions. `/admin/reviews` supports bounded visibility/movie filters and direct hide/restore and spoiler-enforcement actions. `/admin/actions` shows server-filtered history. These routes are lazy-loaded, use existing VYBE tokens and accessible dialogs, and keep controls available at mobile widths. TanStack Query keys start with `['admin', ownerId, ...]`, include filters/page, pass `AbortSignal` for reads, and have no write retries. Successful moderation invalidates that owner's admin cache and the affected movie review lists; authentication changes already clear private caches.

## M3.1C current implementation

The existing `/admin/users` page now offers an active administrator a Create account dialog with username and email. The server-confirmed result reports whether the mail transport accepted the invitation or delivery remains pending, and links to the new account. Admin list/detail show the safe `invitation_pending` marker; eligible details can resend, with a pending state and accurate result. The public `/invitation/accept` page reuses the auth layout and shared fields. It reads the email and token from a URL fragment, immediately strips the fragment from history, validates password confirmation and sends through the shared Axios/CSRF client. Success directs the person to normal sign-in. The page has a no-referrer policy; tokens are not put in local or session storage. Existing `['admin', ownerId, ...]` query keys and account-change cleanup are reused. Create/resend invalidate the current owner's admin queries only and guard async success after an account switch. No new state or animation dependency was added. Hard deletion and later M3 screens remain deferred.

### M3.1C password management UI

Eligible `/admin/users/:id` accounts show Change password and Send password reset actions only to active administrators. Each opens the existing accessible Dialog with a required reason and server-confirmed feedback. Direct change also collects the new password, confirmation and acting administrator's current password through masked shared Inputs with the existing reveal control. Inputs remain in component state only, clear on success or close, and remain available after validation failure. Mutations use shared Axios/CSRF, no automatic retries, owner-scoped query invalidation and the existing account-change guard. Reset delivery messaging distinguishes transport acceptance from inbox receipt or an unconfirmed delivery.

The lazy `/password/reset` auth page reads email and the broker token from a URL fragment, removes the fragment from history, and keeps the token only in component memory. It requires password confirmation and presents the same generic invalid/expired-link feedback for failed token validation. On success it clears sensitive fields and directs the person to sign in again. The existing no-referrer page policy, auth layout, responsive VYBE styles and reduced-motion behavior apply. No new UI or state dependency was added.

## M3.1B current implementation

`/admin` links verified administrators to lazy `/admin/users` and `/admin/users/:id` screens. Moderators retain their landing without user-management links. A nested `RequireUserManager` guard checks the current `/me/access` result; Core checks each request again. The list uses URL-backed page, search, role and account status filters, a 350 ms search delay, server pagination and a mobile card presentation. Details show the approved account projection and accessible edit, role and status dialogs. Role/status confirmation requires a reason, waits for server success, and reports errors without changing the displayed state. Shared Axios and CSRF bootstrap, Dialog, Input, Button and semantic VYBE colors are reused; no animation or state package was added.

Private keys are `['admin', ownerId, 'users', filters]` and `['admin', ownerId, 'user', targetId]`; reads forward AbortSignal. A successful mutation invalidates only that owner's admin queries and, for self changes, auth/access. Writes have no retry. A 401/403 from an admin read or write removes that owner's admin cache and refreshes auth/access as appropriate. The existing login/logout flow cancels and removes non-auth caches on account changes; a pending mutation checks current owner after CSRF bootstrap and before publishing success. M3.1C invitations are implemented above; M3.2 moderation and M3.3 recommendations remain planned below.

## Admin and moderation

Implemented `/admin/users` and `/admin/users/:id` require administrator access; `/admin` remains the role-specific landing. Future `/admin/reports`, `/admin/reports/:id` and `/admin/reviews` would require moderator or admin. Current user screens have edit, role and status dialogs, responsive list presentation, filters, pagination, loading, empty and retry states. Account creation and invitation acceptance were added in M3.1C. Hard deletion is deferred pending a retention decision; report/review navigation belongs to M3.2. Pending or failed actions retain their server-confirmed state.

Use an owner-scoped `['me', userId, 'access']` query for `/me/access`, enabled only after verified auth. A role-aware route guard and navigation are convenience only. On login/logout/account change use existing cancellation and non-auth cache removal. On 401 clear private state and recheck auth; on 403 refresh access and display the actual restricted/permission message, rather than the current generic verification-only mapping. On demotion, remove admin caches and leave the protected view. No role data in localStorage; every backend request checks live authorization.

Suggested query keys include `['admin', userId, 'users', {page, perPage, q, role, status}]`, `['admin', userId, 'user', targetId]`, `['admin', userId, 'reports', filters]`, `['admin', userId, 'report', id]`, `['admin', userId, 'reviews', filters]` and `['admin', userId, 'actions', filters]`. Include all query parameters. Pass AbortSignal on reads; no automatic write retry. Guard async callbacks against changed account/role, including after CSRF bootstrap. A user role/status write invalidates that user and user lists; if it affects the current account, refresh auth/access. Moderation updates the target review, relevant report/list/action queries and public review pages for that movie; do not invalidate unrelated movies, ratings or library.

Review cards gain a report action for verified active users except their own review. A reusable Dialog presents reason and optional description, labels controls, traps/restores focus, prevents duplicate submission and reports the actual 201/200 outcome. The moderator queue presents report reason, target availability and minimal author identity; it never claims a deleted review is still present. Hide, restore, spoiler and dismissal require reason/confirmation as appropriate. Public list never receives hidden reviews. Owner review editor receives separate author/effective spoiler state and visibility; an enforced spoiler indicator cannot be switched off by the author. Existing plain-text escaping and explicit spoiler reveal remain. Review-body spoiler concealment is UI reading behavior, not data access control.

## Home: For You

Add a lazy or small `features/recommendations` module with typed API method, hook, `ForYouSection` and explanation caption; embed it in `PopularMoviesPage` without redesigning the page. Reuse MovieGrid/MovieCard, MovieState and skeletons. Verified signed-in users get a bounded recommendation query `['me', userId, 'recommendations']`; guests see existing Home/popular content and a sign-in invitation rather than a private call. During verification, keep existing verification flow. Cold-start response is clearly labelled `Popular to explore`, not personalized. Missing features never produce invented reasons.

The recommendation section independently handles loading, empty, cached/stale (with a clear freshness note), safe error and retry. A failure must not block the existing popular feed. Use owner-scoped query keys, AbortSignal and existing auth-change cancellation/removal. After confirmed rating, watchlist, watched or collection-membership writes (including deleting a collection), invalidate only that owner's recommendation query in addition to existing feature keys. Cache server-side using the database revision; a React invalidation alone does not invalidate a server cache. User-triggered refresh refetches; do not bypass server load bounds or retries.
