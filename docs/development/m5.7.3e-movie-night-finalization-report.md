## Implementation decisions

- The existing authorized shortlist section supplies its server totals and current shortlist page to a dedicated finalization component. Private query DTOs are not copied into component state. A confirmation retains only the query's monotonic update revision, conflict marker and the host's explicit tied TMDB selection.
- An active eligible host of a scheduled event sees **Finalize Movie Night**. It requires server-confirmed positive total votes and a nonempty server leader set, and is disabled while totals are fetching/reconciling or an event content/finalization mutation is pending. The voting-open flag/start deadline does not govern finalization. Guests/restricted actors have no finalization controls.
- Sole leader confirmation names the available movie or its TMDB fallback and submits `{}`. Ties offer only the complete server `leaders` list and require an explicit radio selection; the payload is `{tmdb_id}`, never a Core candidate ID. Counts/partial pages never calculate a winner.
- Shared Dialog supplies focus containment, Escape behavior and restoration. Safe initial focus is **Keep voting results**; confirmation explains irreversibility and closure of voting, nominations, RSVP and management. Network/server errors remain accessible inside the active modal. Neither repeated clicks nor permission restoration can duplicate an unresolved write.
- A fresh authoritative voting read conservatively retires confirmation, even when its resulting values are unchanged. Changed/tied/stale selections and 409/422 conflicts require a new review and explicit confirmation, with a safe review notice. `MOVIE_NIGHT_TIE` and leader IDs remain parsed by the approved error infrastructure; fresh GET votes supplies selectable current leaders. There is no automatic resubmission, replacement selection or optimistic finalization.
- The existing finalization mutation immediately applies the returned authoritative terminal event to authorized detail caches, supersedes older private reads, and refreshes lists/inbox/totals. Existing terminal protection and owner/membership guards remain intact. No write response is used to infer a winner.
- The existing feature-local command hook now includes finalization in owner/event content request locks and reports finalization conflicts. Permission/dialog loss retires presentation and clears errors/selection without clearing the unresolved request lock. Confirmed writes still reconcile through the mutation hook while restricted originating UI cannot display completion state. Leaving the UI never triggers completion navigation.
- A small error-path guard now requires the original request lifetime to remain current before a conflict invalidates event queries. Owner ID equality alone was insufficient after same-account logout/relogin or event revocation. Late errors cannot disturb fresh private queries in a newer session; unrelated events remain isolated.
- Finalized host/accepted views use only stored `finalized_tmdb_id`, even when informational final totals remain tied or name other leaders. The winner panel reuses MovieCard's poster/title/year/rating and stable poster fallback; finalization time uses the event IANA timezone. Schedule/location/safe meeting link and host-only roster remain on the existing authorized detail page. Invalid lifecycle actions disappear and shortlist/totals remain read-only.
- Available current-page winner metadata is reused; an off-page/missing winner uses one existing public **Core** movie-detail query. Failure preserves the final event and a stable TMDB-ID fallback, without per-candidate requests or browser calls to Catalog/TMDB. Public metadata cache contains no private event DTO; revoked readers cannot mount/display the private winner panel.
- The approved SQL dashboard partition, Finalized filter, pagination, URL/back navigation and minimal closed pending/declined inbox are unchanged and exercised by mocked regression cases.

### Shared synchronous exclusion

Root cause: `useIsMutating` supplied a render-time snapshot, while each command-hook instance had its own ref lock. That combination did not itself establish synchronous exclusion between separate shortlist/finalization consumers before React notifications/rerenders.

Correction: a QueryClient-local WeakMap admits exactly one command synchronously per owner/event/access generation. The hook acquires before calling `mutateAsync` and releases only in `finally`, after settlement. It covers nomination, removal, voting and finalization without a queue or retry. Restriction/dialog retirement does not release it. The existing request context is checked at admission; a session/event revocation advances the authorization generation so old cleanup cannot unlock a newer command. Unrelated owners, event IDs and QueryClients remain independent. Existing React Query pending observations still render disabled states; they are no longer the sole cross-consumer admission check. Core’s locks/authorization remain authoritative across clients/tabs.

Eight new unit cases cover each command excluding all four same-event command kinds in one JS turn; QueryClient/owner/event isolation; restriction/restoration; and old session/event cleanup versus a fresh generation. The new mounted overlap group captures the actual React onClick callbacks from the two separate consumers and invokes them synchronously in both orders, before React can replace their closures. It holds the first finalization or vote response, asserts exactly one transport request, exercises restriction/restoration while held, and verifies the rejected command is neither queued nor retried after release.

### Failed conflict reconciliation

Existing shortlist rendering already withheld vote props after a query error. The correction makes the stronger rule explicit: finalization eligibility requires a successful, non-invalidated authoritative voting query, and synchronous command admission additionally requires an idle successful query with positive votes/current leaders. A cached positive total is insufficient while invalidated, fetching or failed. The latter check also rejects a retired callback with an otherwise stale `allowed` closure. Closed confirmations lose their radio selection; only a fresh successful voting read and new explicit interaction can recover. Safe fresh-review notices remain separate from permission-loss presentation state.

Six new unit cases cover cached invalidated/error queries and the four tie/stale-selection × HTTP 503/network read-failure combinations using actual adapters, QueryObserver, invalidation and explicit refetch. They verify retained cached DTOs cannot enable confirmation, no finalization retry, and successful explicit recovery. The new mounted reconciliation group exercises all four combinations, invokes the retired confirmation callback after the failed read, and confirms no second write or dialog is restored. HTTP 503 cases also lose/restore account permission; network cases switch sessions away and return. All remain disabled until a successful voting retry, then require a new unselected tie dialog with exactly the current leader IDs and an explicitly confirmed new write.

Browser callback instrumentation uses the installed React DOM props key only in the synthetic test harness. It deliberately bypasses native modal background inertness to exercise stale handlers and shared hook admission; production code exposes no test hooks. This harness detail is tied to the installed React version and may need adjustment on a future React upgrade.

## Final confirmation-admission correction

The shared command-exclusion correction is **source-reviewed and approved**; its `commandExclusion.ts` implementation is unchanged in this pass. This narrow follow-up binds finalization to its original confirmation. **This admission correction is included in the source-reviewed, operator-approved M5.7.3E; basic live acceptance is recorded above.**

Root cause: the earlier synchronous guard checked whether voting data was currently usable, but created a new request context at submission. A retired callback could therefore see a newer successful voting query or restored session as usable. Render-time dialog retirement alone did not bind that callback to the authority under which it was opened.

Correction: opening a dialog captures a feature-local admission token with the original request context, query identities, exact voting update counter and account-access update counter. Submission checks that token synchronously before acquiring the existing shared lock or starting a mutation. Query replacement is rejected even if update counters coincide. The original session/event authorization context must remain current, voting data must still be successful/non-invalidated/idle with valid server leaders, the account must remain active, and the current detail must remain scheduled. No response timestamp or locally computed winner establishes authority.

Explicit close, permission/revision retirement, replacement by a new dialog and component unmount synchronously retire the token. Restoring permissions, returning to the same owner in a new session or obtaining successful fresh voting data cannot reactivate it. A new dialog receives a separate token and starts with no tied-leader selection. Existing unresolved-request exclusion and mutation reconciliation remain unchanged: retirement cannot release a pending request lock or prevent a confirmed server response from being reconciled safely. No private query DTO is copied into a draft; the guard retains identities/counters and lifetime checks.

Nine new focused cases cover unchanged/changed successful voting reads; restriction/restoration without a voting refresh or intervening render; logout/relogin and switch/back to the same owner; event revocation followed by fresh authorization; a replacement voting query with the same update count; explicit retirement versus a newly opened token; and lifecycle closure before a render.
