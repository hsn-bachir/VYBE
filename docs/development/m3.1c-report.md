# M3.1C engineering report — administrator account invitations

Date: 2026-11-04. Branch: `feature/roles` at `d4a4707` when work began. M3.1A and M3.1B were already present as uncommitted work. This slice preserved them; no commit, branch switch, merge, push or PR was made. Review and checkpoint A/B separately before staging this slice.

The starter `password_reset_tokens` table exists but has no application password-reset route; invitation secrets use a separate table. ## Database and invitation architecture

Migration `2026_11_04_000001_create_account_invitations_table.php` adds `users.invitation_pending` with false default and `account_invitations` with unique user FK (cascade delete), unique SHA-256 token digest, current normalized email, indexed expiry and timestamps. Rollback drops the new table and marker while preserving users. The `AccountInvitation` model exposes no token hash in serialization. Core generates 32 random token bytes (64 hex characters), stores only their digest and binds the row to the invited account's current email. Expiry defaults to 60 minutes via `INVITATION_EXPIRES_MINUTES`. A user has at most one active invitation; resend replaces its digest. Acceptance deletes the row. Email edits delete the row, requiring resend. Ordinary registration remains unchanged.

## Backend API, authorization and mail

`POST /api/v1/admin/users` accepts only normalized username/email. A verified active administrator creates an active ordinary unverified account with a random unusable password hash and `invitation_pending=true`. Account, token and `user.created` audit commit in one transaction before sending mail. Duplicate or unexpected fields return 422. `POST /api/v1/admin/users/{id}/invitation` allows only an eligible pending active ordinary user, replaces the token and commits `user.invitation_resent` audit. It returns the same 404 for absent and ineligible targets and is limited to 3/hour/target plus existing administrator write limits. Both endpoints use the existing session/CSRF and private no-store responses. The administrator DTO adds only `invitation_pending`; no token or password appears in API or audit payloads.

`POST /api/v1/auth/invitations/accept` uses the guest-facing web/CSRF stack, 5/minute/IP and 5/hour/token digest. It applies the existing registration password rule. It locks user then invitation, rechecks digest, current email, expiry, active ordinary-user state and pending marker, then hashes the password, verifies email, clears pending and deletes the token atomically. Invalid, expired, replaced and used tokens share one generic 422 invitation error. Success is 204 and does not start a session. Account creation and resend lock active administrators in ID order, then the target, matching M3.1B's lock order. The unique user FK and digest constraints remain the database authority. SQLite feature tests exercise rollback and replacement; true concurrent MySQL transactions remain unverified.

The invitation Mailable links to `/invitation/accept#email=…&token=…`; fragments are not sent in HTTP requests. The frontend strips the fragment from browser history and sets no-referrer policy. Mail dispatch occurs synchronously after the transaction. `invitation_delivery:"accepted"` means the transport accepted the message, never inbox receipt; `"pending"` means dispatch failed or the configured transport could log the link. The `log` mailer and aggregate transports containing it are blocked for invitations; the default local `.env.example` therefore requires a non-logging mailer for actual delivery. Failure keeps account/token for explicit resend. The endpoint does not retry automatically or create another account. Set `FRONTEND_URL`, `MAIL_MAILER` (SMTP or another non-logging transport), mail credentials/from address, and optionally `INVITATION_EXPIRES_MINUTES` before rollout.

## Frontend and UX

`/admin/users` has an active-admin Create account dialog with labelled fields, pending guard, field errors and server-confirmed delivery feedback plus a link to the created account. List/detail show the pending marker. Eligible detail pages can resend, with accurate accepted/pending/error feedback. `/invitation/accept` reuses the VYBE auth layout, shared password fields and Axios/CSRF client; it handles incomplete links, password errors, invalid/expired links, network errors and successful activation with normal sign-in. It holds the token in component memory only, never browser storage. The shared Dialog provides focus trapping, Escape and restoration. No UI dependency or animation package was added.

Admin queries remain `['admin', ownerId, 'users', filters]` and `['admin', ownerId, 'user', targetId]`. Creation/resend invalidate only the current owner's admin root. Mutations check the current account after CSRF bootstrap; success callbacks verify the owner again. Existing logout/login cancels and removes private non-auth queries. No change to the five-field `/auth/me` DTO, registration or other private feature keys.

## 2026-11-05 addendum — administrator password management

Core already had a hashed `User` password cast, the Laravel broker and `password_reset_tokens` table, the M3.1B actor/target lock and audit service, and existing Sanctum/CSRF protection. No reset-completion route or frontend reset form existed. The new Core migration `2026_11_05_000001_add_password_session_version_to_users_table.php` adds a nullable private session version and preserves users on rollback. No new reset or audit table was created. Catalog was unchanged.

`PUT /api/v1/admin/users/{id}/password` returns 204 after an active verified administrator supplies their own current password, a confirmed registration-strength new password and a reason. The service locks and rechecks actor/target, rejects self, other administrators and invitation-pending accounts, hashes the password, rotates the target's session version and remember token, revokes same-connection database sessions and reset tokens, and writes `user.password_changed` atomically. Role, status, email and verification remain unchanged, including banned/deactivated status. A password-free notification is attempted after commit; failure is safely logged and does not undo the change. The response does not claim mail delivery.

`POST /api/v1/admin/users/{id}/password-reset` accepts a reason and returns 202 with `reset_delivery` (`accepted` or `pending`), never a token. It uses the Laravel broker's hashed one-use, 60-minute token and 60-second cooldown; token issuance and `user.password_reset_initiated` audit commit together before notification. The log mailer is blocked for token-bearing messages. `POST /api/v1/auth/password/reset` uses the guest-capable web/CSRF stack, locks the account and completes a broker reset atomically with password hashing, token consumption and session invalidation. Unknown accounts and invalid/expired/used links share one generic 422 token error. There is no public reset-link request endpoint. Email edits delete outstanding old-address reset tokens. Audit contains actor/target IDs, action, reason and timestamp with empty details; no password, hash, token, session ID or request payload is recorded. Restrictive per-actor, per-target and completion limits apply.

Database sessions on the Core connection are physically deleted inside the transaction. The new version is stored in the server-side session on login and checked on authenticated requests, so stale file-backed sessions lose access on their next request. A reset performed by the currently signed-in target also invalidates that browser session. The five-field `/auth/me` resource remains unchanged and the private version is hidden from model serialization.

The existing `/admin/users/:id` page now shows Password Management only for eligible accounts to active administrators. Separate dialogs collect direct-change credentials/reason or reset-initiation reason using shared masked Inputs and Dialog. They prevent duplicate submission, show field errors and clear password fields on success or close. The lazy `/password/reset` page reads a URL fragment, removes it from history, keeps its token only in component memory and uses shared Axios/CSRF. Existing no-referrer policy applies. Admin mutations do not retry and invalidate only owner-scoped admin queries after confirmed success.

Core `php artisan test --compact --no-ansi` passed **352 tests, 3251 assertions**, including **10 password tests** covering authorization, password hashing and actual old/new login, session invalidation for database/file drivers, token use/expiry, CSRF, limits, audit rollback, notification failure, migration rollback and safe reset links. Frontend `npm test` passed **181 tests in 10 files**; `npm run lint`, `npx tsc -b --noEmit` and `npm run build` passed. Initial JS is 504.24 kB / 169.38 kB gzip (previously 503.79 kB / 169.28 kB); the prior 500 kB warning remains, while admin detail and reset form stay lazy chunks. A new real-browser password journey, isolated MySQL migration/concurrency, external SMTP receipt, hosted CI and human review were not verified. MySQL80 was stopped during earlier local troubleshooting; no shared database migration or wipe was attempted.
