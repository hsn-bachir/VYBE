## B. Database implementation

New Core migrations:

- `2026_11_01_000001_create_collections_table.php`: id, user_id, name VARCHAR(100), nullable description TEXT, Laravel timestamps; FK to users with cascade; `(user_id, created_at, id)` listing index.
- `2026_11_01_000002_create_collection_movies_table.php`: id, collection_id, unsigned BIGINT tmdb_id, timestamps; FK to collections with cascade; UNIQUE(collection_id, tmdb_id); `(collection_id, created_at, id)` listing index.

`User::collections()` → `Collection::movies()` → `CollectionMovie`. Each collection belongs to a user; each membership belongs to a collection. Explicit fillable lists contain only editable names/descriptions or movie references. There is no movie metadata copy, Catalog FK, redundant membership owner, special Favorites table or new database in the application architecture.

Names trim outer whitespace, preserve capitalization, and permit exact duplicates and case variants. IDs define identity. Schema inspection and SQLite/MySQL tests verify that no name unique index exists. Descriptions trim outer whitespace and normalize blank to null. Cascades affect only the deleted owner's/collection's records; collection deletion preserves Watchlist and Watched.

## C. Backend API

All routes below start at `/api/v1`:

| Method | Path | Successful behavior |
| --- | --- | --- |
| GET | `/me/collections` | Paginated collection objects/counts; optional contains_tmdb_id annotates, never filters |
| POST | `/me/collections` | 201 collection; repeated names create separate IDs |
| GET | `/me/collections/{id}` | 200 collection summary/count |
| PATCH | `/me/collections/{id}` | 200 updated name/description; clearing description supported |
| DELETE | `/me/collections/{id}` | 204; absent/non-owned returns 404 |
| GET | `/me/collections/{id}/movies` | Paginated, batch-enriched memberships |
| POST | `/me/collections/{id}/movies` | 201 new membership; 200 existing with original timestamps |
| DELETE | `/me/collections/{id}/movies/{tmdb_id}` | 204 including absent membership in an owned collection |

The existing `data`/`meta` envelope is retained. Lists default to 20, maximum 50, pages 1–10000; created_at DESC then id DESC. Collection count/EXISTS projections require two listing SQL queries including pagination count, independently of row count. No metadata HTTP occurs for collection cards or empty movie pages. Membership responses include collection_id, tmdb_id and created_at; enriched rows also carry movie/metadata_status.

Validation: required trimmed name ≤100; nullable description ≤2000; at least one allowed PATCH field; strict body integer TMDB IDs and canonical route/query IDs in 1–2147483647; unsupported mutable fields rejected. DELETE accepts no fields. All object queries resolve through the authenticated user's collections. Missing and non-owned objects share sanitized 404 JSON. Reads/writes reuse Sanctum sessions, explicit web/CSRF, verified email, private no-store and the existing shared 120-read/60-write per minute owner limits. CORS now permits PATCH. 419/429 responses preserve status/Retry-After without debug traces; unexpected collection 500s are sanitized.

`LibraryMetadata` extracts the existing M2.1 reference confirmation and batch enrichment. Both LibraryService and CollectionService consume it; MovieCatalogClient and Catalog are unchanged. New references require one batch confirmation; unresolved cache entries yield 422 with an instruction to open details, not a fabricated TMDB 404. An unavailable Catalog yields 503 for new saves. Duplicates and removals need no Catalog. Movie pages preserve every Core row, total, order and removal action with available/missing/unavailable status.

New additions confirm outside a transaction, then re-resolve/lock the owner-scoped parent before `firstOrCreate`. This prevents a collection deletion between the final parent check and INSERT. Deletion during confirmation becomes 404. Database uniqueness remains the final membership authority. Updates/removals also protect the parent with short local transactions; no HTTP is performed while locking.

## D. Frontend implementation

New `features/collections` owns typed API functions, query hooks, DTOs, pages, components, styles and tests. Protected overview/detail routes are lazy. LibraryHeader supplies the shared three-tab navigation; existing cards, grid skeletons, pagination, image fallbacks, guards, Axios, buttons and input components are reused.

Overview cards display name, count, optional description, collection ID for duplicate-name context and visible edit/delete actions outside the navigation link. Details show metadata/count, paginated shared movie cards, removal, editor and deletion confirmation. Loading, empty, Core failure, absent collection and missing/unavailable Catalog states remain distinct. Empty collections link to Discover.

Movie Details adds a lazy Save dialog beside Watchlist/Watched. It identifies the movie, fetches bounded pages with contains_tmdb_id, disables pending rows, and changes checks only after API success. Each row writes independently. Previous/Next preserves confirmed cached states and reopens with a refetch. CollectionForm is reused for overview creation, editing and inline create-and-save. Inline creation distinguishes the two operations; a failed membership leaves the new collection and clearly offers retry. Delete waits for success before closing/navigating. Failed writes retain forms/collections and never announce success.

Numeric-ID query keys, fixed per_page=20:

```text
['library', owner, 'collections', {page, contains_tmdb_id: movieIdOrNull}]
['library', owner, 'collection', id]
['library', owner, 'collection', id, 'movies', page]
```

Private reads use 30-second stale time, forwarded AbortSignal, no retries and no focus refetch. Save forces refetch on opening. CRUD invalidates all owner collection list/modal variants; edit updates affected detail; deletion removes detail/movie caches. Membership success updates confirmed flags and invalidates affected collection/count/list views. It never invalidates discovery, public media or Watchlist/Watched. Writes bootstrap CSRF, verify current owner before dispatch, and guard completion/cache updates against changed accounts. Existing auth cancellation/cache clearing and 401/403 handling are reused; writes do not automatically retry.

## H. Known limitations and deployment

- Live TMDB delivery, email delivery, third-party YouTube playback, hosted CI and human review were not verified by this task. Existing fake-provider suites cover the unchanged boundaries. Instructor confirmation of microservice grading expectations remains outstanding.
- Offset pages can shift during concurrent collection edits; no snapshot guarantee. Multiple tabs/users see changes on refetch rather than push. Lists remain bounded; Save uses page navigation rather than fetching every collection.
- Create and save remain two operations. Closing during an in-flight membership may defer its visible outcome until reopening/refetching; checked state always comes from confirmed data. A successfully created collection is retained if save fails. No distributed transaction or bulk replacement was added.
- Library/collection rows remain usable with missing metadata, but new saves still require Catalog confirmation. There is no collection cover upload, sharing, public collection API or special Favorites entity.
- Run `cd backend && php artisan migrate` in the reviewed deployment process before serving the M2.2 Core/frontend. No Catalog migration, new secret, new environment variable or dependency is required. Existing service URL/token/session/CORS settings still apply; rebuild cached configuration to include PATCH if used. Rollback drops collection data and needs a deliberate retention decision outside disposable tests.
