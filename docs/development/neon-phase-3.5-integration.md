# Neon PostgreSQL migration — Phase 3.5 local integration and deployment readiness

Date: 2026-11-10. Branch: `feature/neon-postgres-migration` (`682c7df98be9ea262271d57b597fe25b79e04c39`). This report records local verification of the checked-out source. **No Neon project or database was created or initialized.** Existing MySQL databases, Firebase identities, and development `.env` files were not changed.

## 1. Decision and current status

Core and Catalog will each start with a **fresh, separate Neon PostgreSQL database**, initialized by their own Laravel migrations. Existing local MySQL rows, sessions, caches, queues, numeric SQL user IDs, user-generated movie data, and Catalog metadata will **not** be transferred. Existing Firebase identities stay in Firebase; their SQL mappings must be established through the application's normal verified sign-in/onboarding or the existing operator-controlled link command. The data-preserving import/reconciliation gates in the [Phase 1 audit](neon-phase-1-audit.md) and [Phase 3 report](neon-phase-3-report.md) are superseded by this explicit fresh-initialization decision; their compatibility findings still apply.

**Locally ready:** complete fresh migrations, full PostgreSQL application suites, actual Core → Catalog HTTP, public SPA discovery/details, database cache and sessions, and a PostgreSQL-backed empty queue worker. **Deployment pending:** independent Neon targets, direct verified-TLS connections and scoped roles, a hosted CI run, and controlled live Firebase/role acceptance. No application defect was confirmed in this phase, so no application code or API contract was changed.

## 2. Isolated local topology and migration result

Docker Compose configuration was available in `compose.postgres-test.yml`; Docker's daemon was unavailable in the Phase 3 local run. For this phase, a temporary **PostgreSQL 18** cluster under the Windows temp directory was bound only to `127.0.0.1:55433`. Its trust authentication was local-only. Two new databases, `vybe_core_integration_test` and `vybe_movies_integration_test`, were created in that cluster, separate from the Phase 3 `_test` databases, the regular PostgreSQL service, MySQL development databases, and Neon. Both used UTC. No database was deleted.

With `APP_ENV=local`, `DB_CONNECTION=pgsql`, `DB_URL=''`, `DB_SSLMODE=disable` **only for local loopback**, and each distinct database name, `php artisan migrate --force` completed **18 Core** and **4 Catalog** migrations; `migrate:status` showed every migration applied. Core has `users`, sessions, cache, queue, library/community and administration tables; Catalog has movies, cache and queue tables. The Core database had **zero users** after migration and still had zero after the guest HTTP/browser run and the failed provisioning check. Core has no `movies` table and Catalog has no `users` table. The internal service token and TMDB token remained server-side.

The two Laravel servers and Vite frontend started against these databases without database errors: Core `127.0.0.1:18000`, Catalog `127.0.0.1:18001`, frontend `127.0.0.1:15173`. These ports, credentials, and fixture data are local test values, not deployment settings.

### Actual HTTP and browser integration

Catalog held one explicitly labelled **local fixture** for TMDB ID 550 before the HTTP check. It was inserted into only the disposable Catalog database; it is not a claim about TMDB content. `GET /api/internal/v1/movies/550` with the internal token returned 200, then public Core `GET /api/v1/movies/550` returned 200 with the same fixture title and ID through the live Core → Catalog HTTP boundary. Internal Catalog detail requests with no token or a wrong token returned **403**. Internal `POST /movies/summaries` returned one stored result for `[550,550,999999]`, reporting requested count 2, returned count 1 and missing ID 999999. Public Core ratings and reviews for 550 returned 200 with zero counts and the documented pagination structure. A guest `/api/v1/auth/me` request with JSON `Accept` returned **401**; `/api/v1/me/profile` also returned 401.

Core popular and search returned 200 through Catalog. The Catalog process picked up an existing locally configured TMDB credential despite an attempted blank shell override, so those two requests and the movie experience UI made **live provider calls**. The provider returned 20 popular items on page 1 and one result for `fixture`; they were not mocked or fabricated. A cached direct Catalog popular response and Core public response had the same 20 IDs in the same order. The isolated Catalog database then held 28 rows (fixture plus provider-fetched metadata), with separate Core and Catalog cache rows. This is local integration evidence, not a reproducible provider assertion; automated provider tests remain faked.

Playwright reached the PostgreSQL-backed home page (20 popular films), discovery page and a movie detail page for the local fixture. The detail page showed empty community ratings and reviews from Core. The experience section also displayed live TMDB data for ID 550, so its cast/trailer are **not part of the fixture assertion**. Guest visits to `/library/watchlist` and `/admin` redirected to `/login`. The sole browser console error was the expected guest `/api/v1/auth/me` 401. Authenticated library, review/rating writes and administrator browser pages were **not manually exercised** because no dedicated live Firebase test identity was configured; their API and frontend test coverage is in the automated suites above.

Core's PostgreSQL `sessions` table acquired guest rows during HTTP/browser use; both applications' PostgreSQL `cache` tables acquired rows; an empty `php artisan queue:work database --once --stop-when-empty` completed successfully on each database. No application job class or dispatch path is currently implemented, so actual queued job processing is **unverified and not a current feature**. Existing suites check bounded admin list queries and Catalog summary batching. The targeted two-process Catalog probes above cover one refresh contention and one concurrent ranking upsert; they are not a sustained load test or a multi-worker HTTP benchmark. Broader write contention, N+1 behavior under load and Neon connection pooling remain unverified. No query, transaction or duplicate-write defect was observed.

## 4. Firebase identity and fresh Core database behavior

Firebase remains the identity provider and Sanctum the browser session layer. The repository's mocked Firebase feature tests passed on PostgreSQL. Source and test evidence establish:

| Scenario after fresh Core migration | Current behavior |
|---|---|
| Valid password-provider Firebase UID has no SQL row | `/api/v1/auth/firebase/session` verifies the recent token, project, revocation and Firebase record, then creates a normal SQL user with that UID, generated unique username and nullable SQL password. Email verification is copied from Firebase; ordinary access remains subject to verification/status middleware. A new SQL ID is assigned. |
| Google/GitHub UID has no SQL row | Social exchange returns **202 `USERNAME_REQUIRED`**. The user chooses a username and `/api/v1/auth/firebase/register` establishes the mapping. No silent social SQL provisioning occurs. Missing/unverified provider email and provider-claim mismatches fail closed. |
| UID already mapped | The existing SQL row, ID and role are reused; verified email/status synchronization and session rotation apply. This covers a user who was linked **after** fresh initialization, not restoration of an old MySQL SQL ID. |
| Firebase email collides with a different SQL account | **409 `IDENTITY_CONFLICT`**. Matching email alone never links UIDs. Operator review and explicit `vybe:firebase-link` are required for an eligible *unlinked* SQL row. |
| Old MySQL-linked Firebase UID signs in after fresh initialization | Its old SQL mapping is absent. It follows the password or social new-user path above and receives a **new** SQL ID, with no former library data, role or administrator status. This is the declared fresh-start policy; do not claim preservation of old account data. |
| Fresh database has no administrator | `app:provision-admin 1` returned failure, “A verified, active account with that ID is required,” and users remained at zero. No email or UID is hard-coded for administrator promotion. |

The automated suite also covers registration retries and UID uniqueness, email verification and collision handling, Google/GitHub onboarding, role/status gates, invitation acceptance, operator linking checks, administrator Firebase identity operations and session revocation. The link command verifies the Firebase UID exists, is enabled and email-verified, matches the SQL email, and is not already linked; it rotates the SQL session version. No live Firebase account was created, modified, linked or deleted in this phase. Firebase TLS/service availability, actual Google/GitHub provider login, email delivery and real session revocation across deployed workers remain unverified.

## 5. Secure first-administrator procedure

1. Complete the **Core** fresh migration, verify `users` count is zero, and arrange an operator-controlled first sign-in. Do not seed a privileged account or infer one from an email address or UID. The application does not currently provide a launch-only registration gate.
2. Have the intended administrator sign in using their **existing** Firebase identity or the normal Firebase registration flow. For a social identity, complete the explicit username step. Require an enabled identity with verified email. This creates or resolves one SQL user; do not recreate the Firebase identity.
3. An operator with direct Core database access verifies the exact `users.id`, `firebase_uid`, normalized email, `email_verified_at`, `account_status='active'` and current `role` against the intended identity. Do not expose the UID or credentials in logs or tickets.
4. On the Core application with its **Core-only direct database connection**, run `php artisan app:provision-admin <verified-core-user-id>`. The command only promotes an existing verified, active row, refuses a second different administrator and is idempotent for the same row. Verify the intended user's role through a fresh authenticated `/api/v1/me/access` call and an administrator read endpoint. Record the operator action through the team's normal change record.
5. If an existing SQL row must be linked to a Firebase identity, investigate the collision first. Only for the explicitly reviewed, unlinked matching-email row, run `php artisan vybe:firebase-link <core-user-id> <firebase-uid>` from Core. It checks the Firebase identity and invalidates previous Laravel sessions. This is **not** a bulk recovery or email-based automatic linking mechanism. A truly fresh Core database normally needs no link command.

## 6. Exact steps once two Neon databases are available

These are **future operator steps**, not actions performed in Phase 3.5. Obtain two independent Neon PostgreSQL databases (for example `vybe_core` and `vybe_movies`) and separate credentials/roles. Each application role needs `CONNECT` to its own database and permission to create/alter the application's objects in its schema for migrations, plus normal table/sequence read/write privileges at runtime. Keep Core and Catalog hosts, names, roles and secrets distinct. Do not grant either service access to the other's database. Use each database's **direct, non-pooler endpoint** for migrations and initial runtime acceptance. Neon's connection details distinguish direct from pooled hosts; pooling has not been validated for this application. [Neon connection guidance](https://neon.com/blog/postgres-support-case-recap) and [Neon TLS verification guidance](https://neon.com/blog/avoid-mitm-attacks-with-psql-postgres-16) provide background.

1. On both deployment hosts, verify PHP compatibility and `pdo_pgsql`/`pgsql` extensions (`php -v`, `php -m`); verify network/DNS access to each direct host. Use a trusted CA bundle for libpq, set `PGSSLROOTCERT` to its path when needed, and test the exact hostname/certificate with `sslmode=verify-full`. Do not weaken production TLS to `require`, `prefer` or `disable` to make a failed certificate check pass. Use the hostname from the Neon direct connection details, not an IP alias.
2. Set **server-side** secrets independently for `backend/` and `services/movie-catalog/` (deployment secret manager or private environment, never `VITE_*`). Prefer explicit variables below; keep `DB_URL` **unset/empty** so it cannot override them. If using `DB_URL` instead, use one direct URL with verified TLS and remove conflicting `DB_*` connection values. Set `APP_ENV=production`, `APP_DEBUG=false`, each service's own `APP_KEY`, Core `AUTH_IDENTITY_PROVIDER=firebase`, `FIREBASE_PROJECT_ID`/`FIREBASE_CREDENTIALS`, `FRONTEND_URL`, `SANCTUM_STATEFUL_DOMAINS`, secure session cookie settings, Core `MOVIE_CATALOG_URL`/`MOVIE_CATALOG_TOKEN`, and Catalog `CATALOG_INTERNAL_TOKEN`/`TMDB_TOKEN`. Keep Core `SESSION_DRIVER=database`; `CACHE_STORE=database` and `QUEUE_CONNECTION=database` have been exercised locally. Core administrator one-use confirmation requires an atomic cache shared by all Core instances. Supply a real mail transport before administrator invitations; the log mailer only leaves them pending. Preserve the existing managed-avatar storage configuration and permissions separately from the SQL switch.

   | Setting | Core (`backend/`) | Catalog (`services/movie-catalog/`) |
   |---|---|---|
   | `DB_CONNECTION` | `pgsql` | `pgsql` |
   | `DB_HOST` | Core **direct** host | Catalog **direct** host |
   | `DB_PORT` | Neon direct port (usually `5432`) | Neon direct port (usually `5432`) |
   | `DB_DATABASE` | `vybe_core` or assigned Core name | `vybe_movies` or assigned Catalog name |
   | `DB_USERNAME` / `DB_PASSWORD` | Core-only role/secret | Catalog-only role/secret |
   | `DB_SSLMODE` | `verify-full` | `verify-full` |
   | `PGSSLROOTCERT` (if needed) | trusted CA bundle path on Core host | trusted CA bundle path on Catalog host |

3. Before any migration, confirm the resolved connection **in each application's own environment** points to its intended new, empty database and role; use a read-only `SELECT current_database(), current_user, inet_server_addr()` via a verified TLS client. Check that the Core and Catalog database names/hosts/roles differ. Arrange restore/backup capability and a deployment rollback plan before opening traffic. Do **not** run `migrate:fresh`, `db:wipe`, seeders or MySQL import scripts.
4. With the **direct Core** connection and application traffic held, run from `backend/`: `php artisan config:clear`, `php artisan migrate:status`, `php artisan migrate --force`, `php artisan migrate:status`. Expect 18 applied migrations and zero users. If deployment caches configuration, rebuild it **after** the correct secrets are present (`php artisan config:cache`). Recycle Core workers/servers so they read the new configuration.
5. With the separate **direct Catalog** connection, run the same commands from `services/movie-catalog/`. Expect 4 applied migrations and zero movies. Rebuild its config cache only after its own secrets are present, then recycle Catalog workers/servers. Keep `MOVIE_CATALOG_TOKEN` equal to the server-side `CATALOG_INTERNAL_TOKEN`; never expose either token to the SPA.
6. Check Catalog's authenticated `/api/internal/v1/health` and a provider-backed Catalog request, then Core's public `/api/v1/movies/popular`, search and detail through Catalog. Check Core guest 401 and a complete Firebase session/verification flow with a controlled identity. Check database-backed session, cache, library/community and administrator reads/writes with dedicated acceptance accounts, then follow Section 5 to provision the first administrator. Verify API shapes against [contracts](../api/contracts.md). Stop if either service resolves to the other's database, TLS cannot verify, or identity collision occurs.
7. Point the frontend only at Core. Validate authenticated personal library, rating/review, profile and admin UI with controlled accounts. Run the CI MySQL/PostgreSQL/frontend lanes on the intended PR and inspect their **actual** hosted result. Monitor connection errors, failed jobs, cache/session behavior and duplicate writes before considering a pooled runtime endpoint; do not infer pooler safety from these direct-connection tests.

## 7. Issues, changes and remaining blockers

**Confirmed issues fixed in Phase 3:** PostgreSQL rollback constraint syntax, Boolean aggregate portability, Catalog numeric width/range, PostgreSQL test isolation and seeder compatibility. Phase 3.5 found **no additional application defect**. The temporary `X-Internal-Token` manual probe returned 403 because the real contract header is `X-VYBE-Service-Token`; the corrected request passed. This was a probe mistake, not a code fix. The Catalog's live TMDB calls are recorded above so they are not mistaken for mocked integration results.

**Files changed in Phase 3.5:** this report only, `docs/development/neon-phase-3.5-integration.md`. **API/DB contracts:** unchanged. **Permanent configuration/migration changes:** none; two disposable integration databases were initialized locally, and no `.env` was edited.

**Remaining blockers to deployment acceptance:** no Neon targets/roles/credentials or verified Neon TLS path yet; no hosted PR CI run for this HEAD; no controlled live Firebase test identity; no authenticated end-to-end browser acceptance; no sustained multi-worker load or Neon pooler validation. MySQL 8 behavior is covered by CI configuration but was not available locally; local MySQL-family checks used MariaDB. The fresh-start policy intentionally discards all old SQL data and role assignments, so launch operators must communicate and handle the new-account experience before switching production traffic.
