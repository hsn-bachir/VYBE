## Implementation and API

Core owns all behavior. Existing M5.0 models, schema, UTC timestamps, parent-event locking, account access, policies, error envelopes and pagination are reused. No migration, dependency, environment/configuration change, Catalog call, M4 dependency or frontend change is required.

Base: `/api/v1/me/movie-nights`.

| Method/path | Input | Success | Permission |
| --- | --- | --- | --- |
| GET `/{night}/eligible-users` | `query`, optional `page`, `per_page` | 200 paginated Participant | Active, verified, activated host; scheduled before start |
| POST `/{night}/invitations` | `{invited_user_id}` only | 201 `{data:Invitation}` | Active, verified, activated host; scheduled before start; eligible target |
| GET `/invitations` | Optional `page`, `per_page` | 200 paginated ReceivedInvitation | Verified, activated caller; active or restricted; own invitations only |
| GET `/{night}/invitations` | Optional `page`, `per_page` | 200 paginated Invitation | Verified, activated host; active or restricted; all event states |

Participant is exactly `{id,username,avatar_url}`. Invitation is `{id,participant,rsvp_status,responded_at}`. Creation explicitly assigns `pending` and null `responded_at`; host is implicit accepted with no invitation row. ReceivedInvitation additionally includes `movie_night` using the existing safe event summary, including host, start, status and caller RSVP. Location and meeting URL require the existing member-authorized event detail endpoint. Raw models/users are never serialized.

Lookup trims/lowercases a 3–30 character ASCII username prefix, permits letters/digits/underscores, escapes underscores literally in SQL LIKE and never searches email. It excludes the host, already-invited users, restricted/banned/deactivated/unverified/pending-activation targets. This event-scoped lookup is not a public user directory. No following relationship is required.

List pagination is SQL-backed: page 1–10000, per_page 1–50, default 20, `{data:[...],meta:{page,per_page,total_pages,total_results}}`. Lookup orders by username/id; invitations order by id. Received invitations retain all RSVP and event states. Eager-loaded relations keep received-list query count equal for one and eight rows; no production latency benchmark is claimed.

Unsupported inputs and malformed SQL IDs return 422. Unknown/ineligible/self targets share a generic 422 validation message. Duplicate invitations in every RSVP state and capacity beyond 200 invitations/event return 409. Started, finalized and cancelled events reject creation and lookup; exactly `now == starts_at` is closed. All RSVP states count toward capacity. No invitation reset, reinvite, revoke or deletion behavior is introduced.

## Authorization, privacy and M7 compatibility

Routes inherit `web`, `auth:sanctum`, `EnsureAccountAccess`, `EnsureVerifiedAccount`, `PreventAuthCaching` and existing library read/write throttles. Creation also uses `EnsureActiveAccount`; lookup uses the existing active-host invitation policy. Session cookies, CSRF protection with/without Origin, Firebase UID mapping requirements, fresh account status and M7 session-version revocation remain unchanged. All responses/errors are private/no-store. Emails, Firebase UIDs, credentials, roles, account status, bio and private activity are absent from participant projections.

Event-scoped handlers query `visibleTo(actor)` before lifecycle or action checks. Nonmembers, including administrators/moderators, receive the same 404 envelope as missing events. Known invitees cannot invite, search targets or read the host roster (403 while open). Consistent with M5.1, closed-state checks precede mutation authorization after membership scoping. Pending account activation is rejected by existing policy. Restricted verified hosts/invitees retain permitted reads but cannot create invitations or search targets. Banned/deactivated/unverified accounts cannot use the workflows. No privileged-role bypass exists.

**Contract decision:** the host-only roster narrows M5.0's proposed participant-visible roster to this slice's explicit host-listing requirement. Invitees see only their own received invitations. **Notification decision:** pull-based received list only; no email, push or WebSocket delivery. RSVP acceptance/decline HTTP handlers, shortlist/voting/finalization handlers and React UI remain outside M5.2. Existing internal M5.0 transitions remain unchanged.

## Transactions and concurrency

Creation uses `DB::transaction(..., 3)`:

1. Lock/reload the actor with `AccountAccess::lock(..., community: true)`.
2. Load the membership-scoped parent event with `lockForUpdate()`; check scheduled/deadline and authorize the fresh actor.
3. Lock/read an eligible target, reject self/unknown/ineligible targets, check duplicate invitation and capacity.
4. Recheck the deadline after target-lock waits, then save one explicit pending invitation and return its safe projection.

The parent lock is the same serialization point used by M5.0 transitions and M5.1 edits/cancellation. The target user lock serializes eligibility against account moderation writes. Reciprocal host/target account locking can deadlock; Laravel retries transient transaction conflicts up to three attempts. Deadlock exhaustion and unexpected failures retain the existing safe 500 envelope. Exhaustive reciprocal-invitation/deadlock stress testing was not performed.

The existing `mn_invitation_unique(movie_night_id,invited_user_id)` key remains the final duplicate safeguard. Direct SQL can bypass domain rules and is unsupported application behavior. No network request runs inside a transaction. A forced PostgreSQL CHECK failure verifies rollback, no inserted row, safe diagnostics even with debug enabled, and successful subsequent creation.

Real PostgreSQL tests use independent PHP processes and committed fixtures. They hold a deliberate database lock, observe both workers waiting via `pg_stat_activity` (clearing its transaction snapshot between polls), then release contention:

- Two service calls: one success and one 409, exactly one pending row.
- Two direct inserts: one success and one SQLSTATE 23505, exactly one row, proving the database constraint independently of the service.
- Cancellation committed while two service calls wait: both return 409 and no invitation is created. The cancellation fixture is committed directly using the model; this is a fresh-state-after-wait check, not a simultaneous HTTP cancellation test.

The concurrency test checks disposable database eligibility before additive migration/fixture creation; workers also guard testing environment, local PostgreSQL, `_test` name, empty DB URL and disposable flag, and reject development ports 55435/55436. It removes only its own committed fixtures in FK order. Remaining tests use the existing guarded RefreshDatabase harness.
