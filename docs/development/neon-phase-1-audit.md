# Neon PostgreSQL migration — Phase 1 audit

Audited 2026-11-10. This is a read-only assessment of the checked-out `feature/firebase-catalog-core` branch and two local MySQL/MariaDB databases. No PostgreSQL migration, Neon provisioning, schema change, application change, dependency installation, or data transfer occurred.

**Evidence labels:** **R** = confirmed in repository source; **L** = confirmed by read-only query against the local database on the audit date; **I** = inference or recommended future design; **U** = unverified until a disposable PostgreSQL/Neon environment exists. File paths are relative to repository root. Repository schema is the intended contract; the live measurements describe only the local databases observed today.

## A. Executive summary

- **R:** Two independently runnable Laravel applications own separate databases: Core in `backend/` owns accounts, Sanctum sessions and user-generated data; Catalog in `services/movie-catalog/` owns TMDB metadata. Core calls Catalog through `backend/app/Integrations/MovieCatalog/MovieCatalogClient.php`; Catalog authenticates the internal HTTP API through `services/movie-catalog/app/Http/Middleware/EnsureInternalCatalogToken.php`. The React frontend calls Core only. The boundaries in `docs/architecture/system-overview.md` and `docs/api/contracts.md` remain appropriate.
- **R/L:** Core has 17 migration-declared tables plus `migrations` (18 physical tables, 18 migrations applied); Catalog has 6 migration-declared tables plus `migrations` (7 physical tables, 3 migrations applied). Both local databases were reachable. Current measured table-plus-index allocation is about **848 KiB Core** and **336 KiB Catalog**. These are tiny development datasets, not production sizing evidence.
- **I:** Migration is feasible with focused migration/query corrections and a controlled, schema-first import. Risk is **moderate**: existing fresh-up paths appear mostly portable, but PostgreSQL rollback SQL, one Boolean comparison, unsigned type range mismatch, collation semantics, live data transfer, connection/security setup, and PostgreSQL regression coverage need work.
- **R:** `backend/config/database.php` and `services/movie-catalog/config/database.php` already define `pgsql`, but `.env.example` files select MySQL and PostgreSQL `sslmode` defaults to `prefer`. PHPUnit runs in-memory SQLite; CI verifies MySQL only (`.github/workflows/ci.yml`). No PostgreSQL migration or app test was run in this phase.
- **R:** Working tree was clean before this report. HEAD `b182f66` contains committed Firebase work. Local `feature/firebase-auth` points to `3cbc81a`; it is **not an ancestor of HEAD**, and HEAD is not `dev`. Determine whether anything unique on that branch must be reconciled before treating a future migration branch as the integrated baseline. This audit does not alter branches or history.
- **U:** Neon account, project limits, network path, credentials, chosen region, backups, verified TLS, PgBouncer behavior for this application, and a PostgreSQL test run are prerequisites to implementation/cutover, not facts established here.

## F. Migration strategy

**Recommended candidate (I): schema-first Laravel migrations into two isolated disposable PostgreSQL databases, then a deterministic, data-only transfer with explicit table allowlists, validation and sequence repair.** Correct D1–D3 before a final dry run. This keeps Laravel's checked-in schema authoritative and the databases independent. At this small observed scale, a narrow, reviewable Laravel/PHP or Python export/import script with explicit casts, UTC handling, checksums and FK ordering is likely simpler than a general schema converter. Evaluate pgloader as a data-only accelerator if real volume or rehearsal time justifies it. [pgloader's MySQL documentation](https://pgloader.readthedocs.io/en/latest/ref/mysql.html) supports data-only and selected tables, but its defaults can create/drop tables or rebuild constraints/indexes; its `create no tables` path can still manipulate constraints. Test an exact configuration in isolated databases first, never point a default load at the target. On Windows/XAMPP, use a pinned WSL2/container invocation only in a later approved phase; no tool was installed here. A dump plus direct CSV/COPY could also work after typed transformations; copying raw MySQL SQL is unsuitable.

**Import order (I):** Catalog `movies` independently. Core `users` first; then independent library/history/ratings/reviews/collections, `collection_movies` after collections, `reports` after reviews and users, `administrative_actions` after users, invitations after users. Verify every FK and every report target with anti-join checks. Preserve all business PKs, TMDB IDs, Firebase UIDs, normalized account ownership, roles/status/profile fields, review/report/audit timestamps and JSON. Transfer `password_reset_tokens` only if legacy reset state is still active. Treat `migrations` as target-generated. Cache and locks are disposable; allow TTL rewarming and a cold first response. Drain/pause jobs and decide whether failed-job records require retention. For sessions, choose and announce either a validated compatible transfer or intentional global logout; never silently lose authenticated state. Handle invitations as security-sensitive: either transfer only still-valid hashes with expiry intact, or expire/reissue through the application after cutover. Never regenerate Firebase users.

**Sequence repair (I):** After explicit-ID import, for each auto-incrementing table set its PG identity/sequence to at least the imported maximum (using `pg_get_serial_sequence`, `setval` with correct empty-table semantics). Assert next insertion does not collide. Preserve MySQL source untouched and inspect zero dates, `0000-00-00`, encoding, boolean 0/1, JSON documents, large unsigned values, NULLs, timezone and long strings before import. Explicitly test whether source `TIMESTAMP` extraction in the MariaDB session timezone represents the same application-visible time and UTC instant after import, including DST-boundary samples. Run record-count and content-hash/field-level reconciliation on immutable snapshots, not just row counts.

## H. Neon infrastructure and security

**R/I:** Each service already has `pgsql` config with `DB_URL`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_SSLMODE` in its own `config/database.php`; `DB_CONNECTION=pgsql` is a future environment setting. Provision **two Neon projects**, separate roles/credentials and proposed databases `vybe_core` and `vybe_movies`; no application role should reach the other database. Keep credentials in server-side secret storage, not Git or `VITE_*`. Verify DNS, firewall/proxy, correct region, `pdo_pgsql` on deployment PHP and TLS hostname validation. **L:** local PHP 8.5.11 has `pdo_pgsql`, `pgsql`, `pdo_mysql`, `pdo_sqlite` and `openssl` enabled; this does not establish deployment PHP configuration. Use `DB_SSLMODE=verify-full` where certificate chain/hostname validation succeeds, otherwise document the tested secure mode and reason; `prefer` alone is insufficient. See [Neon connection security](https://neon.com/docs/connect/connect-securely).

**I:** Use a direct Neon endpoint for schema migrations, import, dump/restore and any session-level operations; evaluate pooled PgBouncer endpoint for web request traffic after transaction, prepared-statement and session/cache/queue tests. Do not infer that a pooler is safe for every Laravel command. Neon describes transaction pooling and direct-connection cases in its [pooling guide](https://neon.com/docs/connect/connection-pooling). Keep Core's database session/cache/queue availability in the latency budget; Catalog's ranking cache is database-backed while its example session driver is file. Define independent backup/export retention and recovery tests beyond Neon's plan restore window. Preserve internal service token as server-to-server only; Firebase and Sanctum remain unchanged.

## J. Rollback and safety plan

1. **Before any future write:** take versioned, verified backups of both MySQL databases; restore them to isolated copies and run count, FK/orphan and sampled checksum checks. Retain source databases unmodified during rehearsals. Never run `migrate:fresh`, destructive SQL or pgloader drop/create defaults on live/source data.
2. **Before cutover:** freeze Core/Catalog writes and queue consumers, record a consistent source snapshot and high-water marks, drain or explicitly capture pending jobs, decide logout/invitation policy, and take final backups. Run imports only into isolated, newly migrated PG targets. If transfer or validation fails, keep MySQL as sole write source, discard/rebuild only the disposable PG target and retry from snapshot.
3. **At cutover:** validate all table counts and content/relationship checks, sequences, Firebase UID mappings, HTTP behavior, TLS and service isolation before enabling writes. Switch both service secrets with coordinated deployment, keep write freeze until validation succeeds, and monitor error rates/latency. If PG has received **no** new writes, restore MySQL routing from known config and verify services before reopening writes.
4. **After PG writes begin:** reverting connection strings alone loses or splits newly created users, Firebase mappings, reviews, reports, audit events and movie updates. Either halt writes and reconcile a complete PG→MySQL delta with conflict handling and sequence checks, or restore PG from backup/branch and roll forward. Decide the recovery path and accountable operator beforehand; do not claim an automatic rollback. Retain backups and audit logs per policy.
