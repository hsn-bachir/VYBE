# M3.2.5 engineering report — performance and administration UX

Date: 2026-11-06. Branch `feature/admin-ui`, HEAD `d9d8b29 reports and moderation (#20)`. The working tree was clean before this task; all changes below remain uncommitted. No branch operation, push, merge, reset or PR was made. The checked-out source included M3.2 review reporting/moderation and prior M1/M2/M3.1 features. Root/backend/frontend agent guidance and current architecture, API, database and design documents were read before editing. No screenshot attachment accompanied the pasted brief, so the existing UI and new browser captures were the visual evidence.

## Architecture and measured baseline

React calls only Core. Core owns sessions, user data and privileged APIs; its movie adapter calls independently running Catalog over authenticated HTTP. Catalog owns TMDB integration and movie metadata/cache. The task reused Sanctum/CSRF, current-state authorization, Eloquent models, `MovieCatalogClient::summaries`, Axios, TanStack Query, accessible Dialog and the existing VYBE tokens. No Catalog code, database schema, dependency or React Bits component was changed.

[Baseline measurements](m3.2.5-baseline.md) were captured on the existing local development ports 5173/8000/8001, before edits. Five read-only curl samples per endpoint and an isolated guest Chromium session measured the public path. Core popular/search/detail warmed to roughly 0.67–0.75 seconds; direct Catalog endpoints took roughly 0.30–0.33 seconds. Core-only reviews/ratings took roughly 0.33–0.35 seconds. TTFB accounted for nearly the entire API duration, pointing to server/dependency processing rather than response download. Catalog cache hit/miss state, Core SQL timings and TMDB traffic were not observable in those samples. The initial production bundle was 505.67 kB JS (169.65 kB gzip), 50.16 kB CSS (10.46 kB gzip), and a 124.36 kB hero WebP. Admin routes were already lazy loaded.

The baseline browser showed public pages waiting for `/auth/me` before rendering their shell. Movie Details additionally waited for details before starting its experience query. Catalog experience and detail share a cold-cache lock and provider payload, so forcing parallel cold requests could return a temporary failure; this waterfall was retained. Browser request logs also showed cancelled/restarted initial requests in local React Strict Mode.

## Backend changes

`GET /api/v1/admin/overview` returns real counts from bounded aggregate queries plus five recent reports; the user aggregate is available only to administrators. Report listing now supports `status=all`, `target_id` and `compact=1`. Review listing supports `scope=needs_attention|actioned|all`, `actioned_type=hidden|spoiler` and `compact=1`, with a correlated pending-report count. No new workflow flag was added. Omitted scope still means all reviews for existing API callers; the UI passes Needs Attention explicitly. Compact list SQL selects only the first 181 body characters and responses expose a bounded preview, while detail endpoints still expose full authorized text. Existing pagination, role gates and no-store responses remain.

`GET /api/v1/admin/movie-summaries?tmdb_ids[]=...` accepts 1–50 distinct canonical IDs and calls the existing Core-to-Catalog batch client once. Missing metadata remains a fallback title in the UI; upstream failure returns the existing safe 503 response. The admin exception renderer now preserves `CatalogFailure` instead of converting that 503 to a generic 500. Neither React nor Core calls TMDB directly.

Reason validation now requires a nonblank 1–1000 character reason for account restriction, ban or deactivation and for review hiding, including report resolution with `action=hide`. Role changes, restoration, spoiler marking/clearing, review restoration, report dismissal, non-hide resolution, direct password change and password-reset initiation accept no reason; a valid supplied reason remains supported. Audit records store `null` when omitted. Existing account locks, live role/state checks, CSRF, password confirmation, session invalidation, idempotency and transaction/audit coupling remain.

No index or migration was added: the baseline did not isolate a slow SQL query and a disposable MySQL EXPLAIN was unavailable. The SQLite feature test asserts 20-row review/report pages stay within ten SQL statements each; it tests query growth without a fragile time threshold.

## Frontend and UX changes

Public Home and Discover render during a pending auth check, while `RequireAuth` and role guards continue to block private routes. Auth query freshness is five seconds to reduce remount refetches; the verification-success route overrides it with a fresh server check. The shared admin shell now has a sticky desktop sidebar and collapsible mobile navigation. Overview shows real counts and a recent report table. Users, reports, reviews and action history use compact semantic tables, responsive rows, pagination, loading skeletons and current VYBE badges. User details group identity, access, password controls and recent audit activity. User rows have one compact action menu that deep-links to the relevant detail dialog.

Review management has URL-backed Needs Attention, Actioned and All Reviews views. Its title search debounces the existing Core movie search by 300 ms, takes the selected ID internally, and hydrates table movie titles through one bounded admin batch request. Full review text loads only when Inspect opens. The review action menu closes before a dialog opens. Reports default to pending and add resolved, dismissed and all tabs. Report details show the movie title, full available target content and clear decisions. History has readable action labels and server-side target filters. Routine confirmations no longer ask for fabricated reasons; hide/sanction dialogs retain required reason fields. Shared Dialog focus handling, Escape, visible focus, keyboard controls and reduced-motion styles are reused.

New private query keys remain under `['admin', ownerId, ...]`, including overview, sorted movie-ID summary sets, filtered pages and individual reviews. Confirmed writes invalidate the current owner's admin queries and, when a movie is known, its review queries. Existing auth-change cancellation/cache clearing and post-CSRF owner checks remain. The main cinematic AnimatedContent, SpotlightCard and PeekRating/ratings interactions were retained. Nothing was removed solely to reduce bundle size.

## Before and after measurements

Local development, warm server, read-only requests; values are approximate. Browser baseline had one hard navigation per page; after values are medians of three hard navigations with the same guest Chromium/Vite setup. This is directional evidence, not production percentile latency.

## Verification

- Core SQLite: `php artisan test --compact --no-ansi` passed **368 tests, 3,423 assertions**. After a final sparse-ID validation hardening, focused `AdminDashboardOptimizationTest` passed **6 tests, 78 assertions**; the full suite was run immediately before that narrow change.
- Catalog: `php artisan test --compact --no-ansi` passed **96 tests, 422 assertions**; no Catalog implementation changed.
- Frontend: `npm test -- --run` passed **12 files, 189 tests**; `npx tsc -b --noEmit`, `npm run lint` and `npm run build` passed. Build transformed 243 modules; admin routes remain separate lazy chunks. The initial bundle warning remains.
- Browser: fixture-backed Playwright checked all seven admin routes at **375, 768 and 1440 px**, with no document overflow or page errors. It exercised review tabs, title search, a routine reason-free spoiler action and a required-reason hide dialog. Desktop and 375 px screenshots were inspected. A separate guest browser measured Home/Discover/Movie Details timing against the existing local Core/Catalog servers. Browser admin responses and writes were intercepted fixtures, so they do not prove live persistence.
- Core API feature tests cover aggregate role projection, scopes, compact/full text, filters, pagination bounds, 20-row query ceiling, batch count/outage, reason rules, audits and old-client reasons. The existing suites cover Sanctum, CSRF, authorization, report lifecycle, rollback and account-state behavior.

Docker Desktop's Linux engine was unavailable, so isolated MySQL migration/EXPLAIN and concurrent lock behavior were not run. The developer database was not touched. Hosted CI, SMTP, real authenticated browser mutation timings and production profiling are still unverified.
