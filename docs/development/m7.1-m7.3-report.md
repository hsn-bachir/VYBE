# M7.1–M7.3 implementation report — Admin Dashboard and Movie Insights

Verified on 2026-11-23 on `feature/m7-admin-insights`, based on `f5df887`. This slice covers the KPI and watched/rated movie portions of university PDF item 11. The [API contract](../api/admin-movie-insights.md) lists exact counts, fields and authorization.

## Implementation

- **M7.1.** Overview groups all current Core accounts, stored reviews (including hidden), individual VYBE ratings and user/movie watched entries under Platform totals. The existing report, moderation and account-status counts retain their definitions. Moderators receive their existing five-field overview and queue links. An active-user definition belongs to M7.5.
- **M7.2.** Core ranks up to ten movies by the number of distinct members who marked each movie as watched. Equal counts sort by ascending TMDB ID.
- **M7.3.** Core weights each movie average toward the overall VYBE average with a Bayesian prior equivalent to five ratings. Equal adjusted scores sort by rating count descending and TMDB ID ascending. Movie Insights shows the unadjusted average out of five and the number of VYBE ratings.
- **Privacy and metadata.** Movie Insights is available to verified active and restricted administrators through the existing session, role and read-throttle policies. Core sends a single batch of up to 20 unique TMDB IDs to Catalog and retains both rankings during cache misses and outages. It projects only the movie title, poster path and release date. The React route uses the existing admin shell, owner-scoped queries, movie poster fallback and detail links.

Core can deploy first because its overview change is additive. Catalog is compatible through the existing summaries contract. Deployment needs no database migration, environment variable, new dependency or data backfill.

## Performance

Local Windows HTTP measurements used real Laravel Core and Catalog processes, a Sanctum session and independent disposable PostgreSQL 18 databases. Core contained 1,001 users, 1,000 reviews, 100 reports, 30,000 watched rows and 20,000 ratings over 150 movies. Catalog held 141 seeded summary rows. The first sample is the first read of that endpoint after login. Warm values are the median of seven subsequent reads. Database data and PostgreSQL buffers had already been touched by fixture setup.

| Core endpoint | Core SQL statements with array session/cache | Core→Catalog requests | First read | Warm median |
| --- | ---: | ---: | ---: | ---: |
| `GET /api/v1/admin/overview` | 3 | 0 | 315.1 ms | 312.7 ms |
| `GET /api/v1/admin/movie-insights` | 3 | 1 for nonempty rankings, 0 when empty | 908.5 ms | 655.0 ms |

Each measured statement count includes one live account recheck and two domain queries. Persistent session and rate-limit stores add storage work according to deployment configuration. Catalog's existing cache-only batch makes one movie lookup and does not call TMDB. The HTTP timings are local service measurements using seeded metadata and include request and process overhead.

PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` measured 3.73 ms for overview totals, 0.08 ms for recent reports, 13.41 ms for most watched and 5.23 ms for highest rated. The overview uses exact aggregate counts. The watched ranking scanned and sorted 30,000 rows by `(tmdb_id, user_id)` because the existing unique index begins with `user_id`. The ratings plan used a sequential scan, hash aggregation and a window over 150 movie groups. Both final ranking sorts used bounded top-N heapsorts. The watched sort used about 1.7 MB and the measured plans stayed in memory. Growth of the watched table is the primary query-plan concern. The existing indexes and fixture timings support retaining the current schema for this slice.
