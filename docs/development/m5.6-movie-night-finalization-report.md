## Implementation and exact contract

Core exposes the **existing** `MovieNightTransitions::finalize()` through the existing controller and Event resource. No second winner algorithm/service is introduced. The approved authoritative `MovieNightVote::validFor()` cohort and selection logic remain in that transition. The new FormRequest validates route/event IDs, optional selection and an explicit field allowlist.

**POST `/api/v1/me/movie-nights/{night}/finalize`**

- Empty body / `{}`: automatically select the sole highest-voted candidate.
- `{ "tmdb_id": 550 }`: explicitly select a current highest-voted candidate; required when tied.
- The selection is a **TMDB movie ID**, not the Core candidate ID used by PUT vote.
- When supplied, tmdb_id is required/non-null, canonical positive integer 1–2147483647. Event IDs reuse canonical signed SQL-ID validation. Null, malformed/out-of-range IDs and unsupported fields return 422.
- Client status/winner-field/timestamps/vote totals/rankings/leader lists/organizer identities are rejected.
- Success is **200 `{data:Event}`**, with the existing full Event projection and safe host fields.

Example success:

```json
{
  "data": {
    "id": 12,
    "title": "Final cinema",
    "host": {"id":7,"username":"host_user","avatar_url":null},
    "starts_at": "2027-01-16T18:00:00.000000Z",
    "timezone": "Asia/Beirut",
    "status": "finalized",
    "my_rsvp": "accepted",
    "finalized_tmdb_id": 550,
    "finalized_at": "2027-01-15T18:00:00.000000Z",

    "meeting_url": "https://example.com/private-room"
  }

```

The original title/start/IANA timezone/location/meeting URL and all invitations/candidates/votes are retained. One save atomically writes finalized status, winning TMDB ID and UTC finalization/update timestamps. The existing scoped timestamp concern handles PostgreSQL offsets; no global timezone/configuration change is made.

## Winner selection and frontend tie recovery

Under the locked event, count each candidate's valid event votes using `validFor()` (host or current accepted invitee). Later account moderation does not retroactively invalidate a previously valid vote, preserving the approved foundation/M5.5 rule. Pending/declined/outsider fixture votes are excluded. Another event's candidate/votes cannot influence the result.

1. Maximum valid count must be at least one; otherwise return 409 without mutation.
2. Current candidates with that maximum form the authoritative leader set. Candidate-ID ordering makes the exposed tie list deterministic.
3. A sole leader is automatic when selection is omitted. An explicit sole leader is accepted too.
4. Multiple leaders require explicit selection from that set.
5. A nonleader, unrelated ID or foreign-event-only movie ID returns a tmdb_id validation error; stale selections cannot override changed vote totals.

| Condition | Safe response |
| --- | --- |
| No valid votes / empty shortlist | 409 `{ "message":"At least one valid vote is required." }` |
| Tie without explicit selection | 409 `{ "message":"Choose one of the tied leaders.","code":"MOVIE_NIGHT_TIE","leaders":[550,551] }` |
| Nonleading/unrelated/foreign selection | 422 `{ "message":"Choose a highest-voted movie.","errors":{"tmdb_id":["Choose a highest-voted movie."]} }` |
| Repeated finalization or cancelled event | 409 `{ "message":"Movie night is closed." }` |
| Accepted nonhost on a scheduled visible event | 403 `{ "message":"This action is unauthorized." }` |
| Pending/declined/outsider/missing event | 404 `{ "message":"Not found." }` |

Other malformed-input 422, authentication/session 401, account/verification 403, CSRF 419, throttle 429/Retry-After and safe generic 500 envelopes follow existing conventions. Account-code responses remain intact.

`MovieNightTie` is a small HttpException subclass that renders the stable tie code/list while remaining compatible with existing domain callers/tests catching HttpException. It contains only current leading TMDB IDs, never voter choices or identities, and is thrown only after private host authorization.

M5.7 should identify `code === "MOVIE_NIGHT_TIE"`, offer a current listed leader, optionally refresh GET votes/shortlist for counts/display context, and explicitly resubmit that selection. On errors.tmdb_id, refresh totals and require a current choice. Other 409s require checking event state/valid votes. Writes must not be blindly retried. The server always rechecks the current leader set under its lock. After success use stored finalized_tmdb_id, even if frozen informational GET votes leaders still contains a tie.

## Authorization, final visibility and lifecycle

Only the active, verified, activated event host may finalize. Routes inherit the existing first-party `web`/Sanctum session, account/verification, active-state, shared library-write throttle, CSRF and private/no-store behavior. Firebase mapping and M7 session-version revocation are unchanged. Restricted/banned/deactivated/unverified/pending-activation actors cannot finalize. There is no administrator bypass.

The transition now resolves full-private `visibleTo` instead of invitation membership and rechecks `view`, ensuring pending/declined and outsider requests receive hidden 404 before event-state/leader information. Accepted participants can read private finalized details but cannot finalize scheduled events (403). Consistent with approved Movie Night mutation precedence, a visible already-closed event returns lifecycle 409 before mutation permission; no write succeeds. RSVP retains the separate membership scope so pending/declined users can still respond while open.

Host/accepted users can retrieve the existing full event detail: title, safe organizer, scheduled UTC instant, original IANA zone, optional location/link, finalized status, stored winner/timestamp and closed voting state. Pending/declined users retain only the exact seven-field minimal event summaries in listing/inbox, excluding winner/finalization timestamp/location/link/voting data. Outsiders see no event/invitation rows and hidden detail/finalize 404s. Resources are reused unchanged.

Finalization is permitted while **scheduled**, before, exactly at and after starts_at. It intentionally does not call assertOpen or impose a start deadline. Early finalization immediately blocks voting, RSVP, nominations/removal, invitations and edits. Repeated finalization, cancellation of a finalized event and winner/status replacement are rejected. There is no reopen/unfinalize/host-transfer route. Irreversibility is enforced by supported domain transitions/field allowlists, not a new historical SQL trigger; direct SQL outside that protocol remains unsupported.

## Transactions and concurrency

The same three-attempt transaction reloads/locks actor → exclusive event, checks fresh account/private eligibility/scheduled state/eligible-host policy, reads authoritative valid candidate counts, resolves the current winner and performs one atomic terminal save. No network call occurs under the lock or elsewhere in finalization. All compliant votes, RSVP changes, edits, cancellation, nomination/removal and shared-lock tally reads serialize through the same parent event. Host account locking additionally serializes competing organizer actions.

There is at most one successful terminal transition. A stale client choice returns 422 against the current locked leader set; unresolved tie/no-vote/closed-state errors persist no final fields. A forced write failure verifies rollback of status/winner/timestamp while retaining votes and permits a later successful retry. Existing unique/FK/state constraints are preserved; no schema changes are needed.

The previously reviewed invitation host/event/target-user lock cycle is not redesigned; finalization retains actor→event order and existing Laravel transaction retries without adding a target-user lock. Application-wide deadlock/load/retry-exhaustion acceptance remains open.
