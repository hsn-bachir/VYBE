## Implementation decisions

Core exposes the existing foundation RSVP transition through one route and the existing invitation controller/resource. No parallel RSVP service or duplicated domain logic is introduced. No migration, dependency, configuration/environment change, frontend or Catalog change is needed. Shortlist, voting and finalization HTTP endpoints remain unimplemented; the existing internal finalization transition is unchanged.

| Method/path | Input | Success | Actor |
| --- | --- | --- | --- |
| PUT `/api/v1/me/movie-nights/{night}/rsvp` | `{rsvp_status:"accepted"}` or `{rsvp_status:"declined"}` | 200 `{data:Invitation}` | Active, verified, activated invitee responding to their own invitation |

Invitation is the existing `{id,participant:{id,username,avatar_url},rsvp_status,responded_at}` projection. It contains no email, Firebase UID, role, account status, credentials, bio, other invitee, event location or meeting link. The actor comes from the session; client-supplied user/invitation IDs and timestamps are rejected.

- Pending invitees may accept or decline; accepted/declined invitees may change either way while the event is scheduled and before its exact start instant.
- A changed status sets `responded_at` to the current UTC instant and updates `updated_at`. `created_at` remains unchanged. Existing second-precision database persistence remains unchanged.
- Identical repeats return **200** while open and preserve `responded_at`, `updated_at` and `created_at`. Repeats still enforce eligibility, authorization and lifecycle; they return 409 once closed.
- Decline removes only that actor's vote for that event in the same transaction. Repeated decline retains the no-vote invariant without changing response timestamps. Acceptance does not restore a removed vote. Nominations, other users' votes and invitation membership are retained.
- Received invitations, event listings and host invitation listings expose the updated persisted state on subsequent reads. Full event detail is accessible only to the host or a currently accepted participant. There is no notification, shared cache or client refresh mechanism added.
- No explicit withdrawal-to-pending, invitation deletion, host RSVP or host transfer is introduced.

## Authorization and errors

The route inherits `web`, Sanctum sessions, `EnsureAccountAccess`, `EnsureVerifiedAccount`, `PreventAuthCaching`, active-account middleware and the existing library-write throttle. Existing Firebase mapping, M7 session-version revocation and CSRF protection with and without Origin are preserved. Shared authentication code is unchanged. The privacy correction separates the Movie Night full-detail policy from minimal invitation membership authorization. All success/error responses retain private/no-store conventions.

| Status | Behavior |
| --- | --- |
| 401 | Guest, unmapped Firebase-mode SQL identity or revoked session |
| 403 | Account/verification/activation restrictions, or host attempting RSVP while open |
| 404 | Missing/private event; outsiders including administrators receive the same hidden envelope |
| 409 | Known member attempts RSVP at/past start or on cancelled/finalized event, including repeats |
| 419 | Missing/mismatched CSRF |
| 422 | Pending/unknown/missing/nonstring status, unsupported input or malformed event ID |
| 429 | Existing shared write quota exhausted; Retry-After preserved |
| 500 | Unexpected write failure; existing safe generic envelope hides diagnostics |

Membership-scoped SQL precedes lifecycle checks. Consistent with M5.1/M5.2, lifecycle checks precede action authorization for a known member; a host on a closed event therefore receives 409, not an implicit acceptance or mutation. Restricted/banned/deactivated/unverified/pending-activation accounts cannot mutate. Pending and declined eligible invitees retain only minimal invitation reads and RSVP eligibility; direct event-detail requests return hidden 404. There is no administrator/moderator bypass.

## Transactions, locking and deadlock review

`MovieNightTransitions::respond()` now returns the safely loaded invitation. It retains the foundation retryable transaction (three attempts) and performs:

1. Lock/reload the actor via `AccountAccess::lock(..., community: true)`.
2. Load the SQL-membership-scoped parent event with `FOR UPDATE`; check fresh lifecycle/deadline and authorize the fresh actor.
3. Lock the actor's event-scoped invitation with `FOR UPDATE`; recheck the deadline after this additional lock wait.
4. Update only a changed status/timestamps; remove the actor's event vote for decline; load the safe result before commit.

The order is **actor → event → invitation → vote deletion**. RSVP acquires no host/target-user lock and never locks invitation before event. Existing Movie Night mutation paths share the event lock, so competing RSVPs, cancellation/finalization and future compliant vote writes serialize. No provider/network operation runs inside locks. A database-trigger failure on vote deletion verifies that the earlier RSVP/timestamp update rolls back too; a subsequent decline succeeds after trigger removal. This runs on both SQLite and real PostgreSQL, with debug enabled and a safe error envelope assertion.

**Reviewed residual deadlock risk:** M5.2 invitation creation takes host actor → event → target user, while target RSVP takes invitee actor → event. If invitation creation holds the event and waits for the invitee actor held by RSVP, a user/event cycle can occur. The existing three-attempt Laravel transaction retry remains the recovery mechanism. RSVP's invitation lock adds no reverse invitation→event acquisition to application code. Exhaustive reciprocal invitation/RSVP deadlock stress and retry-exhaustion acceptance were not performed. No broad shared lock-order rewrite was added in this slice. Future mutation paths must preserve parent-event serialization and participate in transaction retries.

## PostgreSQL concurrency evidence

Six independent-process cases use committed fixtures, genuine row locks, separate PHP/Laravel processes and `pg_stat_activity` to observe workers waiting before releasing locks:

1. Competing accept/decline calls both complete with 200, leaving one valid serialized final status/timestamp and no vote. Final status follows lock-acquisition order, not launch order; acceptance never resurrects the vote.
2. Concurrent identical acceptance calls both return 200 and preserve the original response/update timestamps and vote.
3. RSVP waits behind an event lock while the existing cancellation service executes and commits; RSVP returns 409 without changing invitation/vote.
4. RSVP waits while the existing internal finalization service executes and commits; RSVP returns 409 without changing invitation/vote.
5. RSVP waits while a fixture moves starts_at to the worker's exact current instant; the fresh event read returns 409.
6. An identical acceptance waits on its invitation row while holding actor/event locks; real time passes the event start, then the invitation lock is released. The second deadline check returns 409 and preserves invitation/vote.

These exercise the domain transition in separate processes, not simultaneous browser HTTP requests. HTTP middleware is tested separately by the feature cases. Cancellation/finalization cases invoke the existing services in the controlling transaction; the rescheduled-start case changes a fixture directly. The invitation-deadline case uses a short real-time wait; other cases use controlled worker clocks.

The test guards local disposable PostgreSQL and exact port 55433 before additive migration/fixture creation. Workers independently guard testing mode, local host, `_test` database, empty DB URL, port 55433 and the disposable flag. Cleanup removes only each test's committed fixtures in FK order; it does not reset any application database. Other feature tests retain the existing guarded RefreshDatabase harness.

## Azure #90 privacy correction before approval

The operator's review identified that the original M5.0–M5.3 visibility assumption violated work item #90: every invitation granted private event details, including location/meeting URL, and summary payloads disclosed finalized result fields. This correction supersedes those earlier contracts and test expectations without changing the schema or restricting legitimate RSVP changes.

| Read surface | Host / accepted participant | Pending / declined invitee | Outsider |
| --- | --- | --- | --- |
| GET event detail | Full existing detail | Hidden 404 | Hidden 404 |
| GET event listing | Existing summary, including finalized result | Minimal allowlist only | No row |
| GET received invitations | Own invitation plus accepted summary | Own invitation plus minimal event allowlist | No invitation row |
| PUT RSVP response | Own safe invitation; host cannot RSVP | Own safe invitation, no nested event | Hidden 404 |
| GET host invitation roster | Host only; accepted invitee cannot read roster | 403 | Hidden 404 |

The minimal event projection is exactly seven fields: `{id,title,host,starts_at,timezone,status,my_rsvp}`. Host/participant identity remains `{id,username,avatar_url}`. Own invitation id/RSVP/responded_at remain available; event-private fields are absent rather than null. Minimal projection does not include location, meeting URL, finalized movie ID/timestamp, cancellation timestamp, voting state, event audit timestamps, shortlist or votes, even after finalization.

`MovieNight::forMember` is used for minimal listings, RSVP and host-action membership resolution. `MovieNight::visibleTo` and policy `view` now require host or accepted status. The separate `viewInvitation` policy retains member eligibility without promoting it to detail authorization. Detail serialization rechecks `view`, so an accepted model loaded before a later decline cannot authorize a detail response using its stale invitation relation. Summary RSVP selection matches the current actor's user ID in the eager-loaded relation. Listing query-count regressions still pass without per-row authorization queries.

Acceptance grants private access; decline atomically revokes it through the persisted status update and removes the actor's vote. Reacceptance before the deadline restores detail access but not the vote. Failed vote deletion rolls back the RSVP update and preserves prior accepted detail access; the failure test explicitly verifies that access too. Lock order, retry behavior, timestamp-preserving repeats, M7 session/account eligibility, CSRF, throttling and private/no-store responses are unchanged. Future shortlist/tally/winner reads must use private-detail authorization, not membership alone; no later-phase endpoint is added here.

Eight additional regression cases cover pending/declined minimal payloads across scheduled/cancelled/finalized events (six combinations), the pending → accepted → declined → accepted access/vote lifecycle, and stale-model detail serialization after decline. Existing foundation, management, invitation and RSVP cases were updated to the corrected model. Host full detail/finalized-result access and roster access are checked across all six combinations; existing outsider/account/concurrency coverage remains in the suites. Reported verification totals below include the correction.
