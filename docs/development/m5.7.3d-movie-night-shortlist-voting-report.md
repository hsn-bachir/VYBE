## Implementation and design

- Replaced the two private detail placeholders with a shared shortlist and Voting summary. Host/accepted members retrieve a 12-entry server page and complete vote totals; pending, declined and outsider detail routes never mount these requests. Restricted verified members and terminal/started events retain read-only access.
- Reused `MovieCard`, `MovieImage` poster fallbacks, rating/year display, `MovieGridSkeleton`, `MovieState`, Avatar, Input, Button and shared Dialog. Poster ratio stays 2:3, long titles wrap, selection uses both text/checkmark and `aria-pressed`, and semantic design tokens/reduced-motion styles remain intact. No unrelated navigation/design changes.
- Metadata comes from the existing enriched shortlist response. Null metadata renders a stable placeholder labeled with the TMDB ID; no per-entry movie API requests are made. Metadata failure does not remove candidates or prevent voting. Names of leaders/selection outside the loaded page fall back to TMDB identifiers rather than fetching individual metadata or inventing global knowledge.
- Nomination dialog reuses Core movie search, shared query normalization/options and AbortSignals. Search is debounced 350 ms, length 1–200, page-limited to the supported 500 pages. Results are hidden until input matches its settled descriptor; query/page keys isolate delayed results. Loading, empty, error/retry, validation, unknown movie and Catalog outage states are supported.
- Nomination submits only TMDB ID, never synthesizes a candidate, disables known existing nominees using the global server totals projection, and respects the server `total_results` 50-candidate limit. Core rechecks duplicate/capacity eligibility. No partial-page candidate/vote counts are treated as global totals.
- Removal uses the Core candidate ID. Controls require host/original-nominator permission and a known server zero-vote row. Missing/failed totals never imply zero. Explicit confirmation defaults focus to Keep movie. Background refresh disables confirmation rather than closing it solely because a read is pending; an actual permission/vote/membership change closes and retires it. Failed removal retains the candidate until authoritative reads say otherwise.
- One server-confirmed vote per member; changing selection uses Core candidate ID. No optimistic selection, withdrawal, additional modes or locally calculated winner. Last confirmed selection survives failed writes. Counts, `my_vote`, `total_votes`, `leaders` and voting state come from Core. The summary displays open only when both server snapshots permit it, the event is scheduled and the known start boundary has not arrived; client time may close presentation but cannot reopen server-closed voting. Account restriction alone does not close the event label. Cached totals, selection and leaders are not changed. Leading TMDB IDs remain provisional; no voter identity lists are exposed.

## Cache, permissions and concurrency

A new **event-local content read revision** covers shortlist/votes separately from the approved event-access and lifecycle-read generations. Successful nomination/removal/vote advances only this revision, cancels affected old reads and refetches cached shortlist/vote projections through Core, including inactive cached projections. Older ignored-AbortSignal responses cannot populate current queries. Detail, roster, lists/inbox and unrelated events are not unnecessarily invalidated by these successes. Session/account/event access revocation still invalidates all relevant private scopes; lifecycle updates also supersede content reads.

Write responses are never merged into shortlist membership or selected vote. Each success triggers fresh server truth, even if a response from an earlier server write arrives after another response with the same timestamp. No dispatch order, response arrival order or `updated_at` timestamp is treated as authoritative ordering. Content read revisions do not govern write lifetimes, so concurrent successful server writes are not misrepresented as failed because another content operation reconciled first. Conflicts refresh content and detail; no mutation retries or replacement selections are introduced. M5.7.3B edit/terminal-state protection remains intact.

Nomination `404 MOVIE_NOT_FOUND` is a movie error, not event-access revocation. Ambiguous candidate-write 403/404 (ownership, deleted/cross-event candidate versus membership) verifies current private event access using the existing guard. A successful probe preserves membership and refreshes relevant projections. A denied private read purges immediately. A failed/unverifiable probe conservatively discards private event caches rather than retaining data under uncertain access. Candidate 403 also refreshes the current account-access query; other owners remain isolated. Unknown movie errors do not trigger that probe or discard valid private data.

Feature-local command presentation is separate from the actual unresolved request lock. `useIsMutating` scopes conflicting nomination/removal/vote controls to owner/event; a synchronous lock prevents repeated clicks before observer updates. Permission loss retires asynchronous UI completion and clears errors/dialog/search state, while unresolved commands retain their locks. Dialog identity is part of the presentation lifetime, so a candidate gaining votes retires a removal completion even when global event permissions remain open. Restoration requires a new explicit action and fresh draft. A confirmed write still reconciles through the data hook even when its originating presentation has retired. Components do not copy private query DTOs into independent state or navigate on content mutation completion.

Decline retains the approved synchronous detail/shortlist/vote/roster/list/inbox purge and event-generation guard. The M5.7.3C completion receipt is untouched. Reaccept mounts fresh authorized detail, shortlist and totals and does not restore a cached old vote. Mocked transport-held voting responses after decline, logout or account switching cannot restore private UI. Atomic vote deletion remains unchanged Core behavior, verified against isolated test databases in this refinement; basic live vote deletion/no-restoration behavior is now operator-confirmed below.
