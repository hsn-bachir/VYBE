# M7.6 — Local movie data management

Implemented on `feature/m7-movie-management`, based on `53750d7` with a clean starting tree. This slice covers the proposed non-destructive movie-management portion of PDF item 11. Instructor confirmation of the full university CRUD expectations remains a separate acceptance decision. M7.7 remains open.

## Delivered behavior

The administrator Movies page browses Catalog persistence with bounded server pagination, local title or TMDB ID search, and freshness and missing-field filters. The detail page displays persisted metadata, unknown genre associations, image fallbacks, full-fetch timestamp, explicit refresh and a public-detail link. Refresh keeps loaded information visible while pending or failing. Query keys are owner-scoped and reads support cancellation. A confirmed refresh invalidates management and movie/genre insight queries.

Core owns permission checks, validation, CSRF and audit records. Verified active and restricted administrators can inspect metadata. Refresh requires an active administrator and the existing 20/minute actor and 60/minute IP write throttles. Catalog owns persistence and provider transport. Each Core operation makes one Catalog HTTP request. Provider calls happen only during explicit refresh on these management routes.

Freshness is calculated from `metadata_fetched_at` and Catalog's existing metadata TTL. Null means not hydrated. A timestamp newer than the TTL boundary is fresh, while a timestamp at or before the boundary is stale. Unknown genres retain null and known-empty genres retain an empty array. Optional missing poster and overview metadata have separate filters.

Manual refresh extends `MovieService::details()` with a force flag while sharing the existing provider normalizer, persistence, lock and cooldown. Lock contention and cooldown return 409. Manual successes also start the configured cooldown, preventing repeated provider requests for a fresh movie. Timeouts, invalid provider metadata and unavailable providers return safe failure responses and preserve previously stored metadata. Provider 404 also retains the local record. An explicit refreshed outcome and a fresh full-fetch timestamp are required by Core before showing success. TMDB's existing bounded transport permits at most two attempts on eligible transient failures.

Core persists `movie.refresh_requested` before making the remote call and completes the same audit record as `movie.refreshed` or `movie.refresh_failed`. Its details contain the fetched timestamp after success. Existing audit history supports movie targets for administrators. An interruption can leave a requested record, and a transport timeout can leave an uncertain remote outcome. These records support later reconciliation. Core and Catalog cannot atomically commit both databases.

## Contracts and deployment

The [management contract](../api/admin-movies.md) defines the Core `GET /admin/movies`, `GET /admin/movies/{tmdb_id}` and `POST /admin/movies/{tmdb_id}/refresh` endpoints under `/api/v1`. Catalog has corresponding service-token routes under `/api/internal/v1/movies/manage`. Deploy Catalog first, then Core and the frontend. No migration, new environment variable, tracking table or dependency is required.

Catalog listing uses a count and bounded page query. ID lookup uses the existing unique TMDB index. Literal title substring and metadata-health filters may scan the Catalog table. Their cost at production data volumes remains unmeasured. Persistent lock/session/cache drivers and valid optional experience capture can add queries beyond the array-cache base-refresh sample. The metadata page remains independent of provider availability.
