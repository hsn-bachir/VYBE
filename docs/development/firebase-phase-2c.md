# Firebase Google and GitHub sign-in (Phase 2C)

## Architecture and configuration

The generic `/auth/firebase/session` exchange also returns `202 USERNAME_REQUIRED` for a new Google/GitHub UID; it cannot auto-provision a generated social username.

The SPA uses the modular Firebase SDK popup flow. It sends only a Firebase ID token and selected provider ID to Core. Core verifies the token, signed `firebase.sign_in_provider` claim, revocation, disabled state, current Firebase UID/email and VYBE SQL ownership. A mapped UID receives the Laravel/Sanctum session; a new UID receives `202 USERNAME_REQUIRED` without a SQL insert. The existing `/auth/firebase/register` endpoint validates the chosen username and creates one SQL user with a null password. Normal requests use only Laravel cookies. No Google or GitHub access token, refresh token, client secret, or provider profile is stored in VYBE.

Enable Google and GitHub in the same Firebase Authentication project used by the SPA and Core. GitHub's Client ID and Client Secret belong in Firebase Console and GitHub's OAuth settings, never in `VITE_*`. Configure GitHub's callback as the Firebase Authentication handler URI shown by Firebase Console. Add the SPA origin to Firebase Authorized domains. The frontend requests GitHub's `user:email` scope; Firebase may still return no usable email. Core returns `422 EMAIL_REQUIRED` and creates no session or SQL user in that case. Add a verified email to the provider account or use another sign-in method. The private-feature email-verification gate remains active if Firebase reports `emailVerified=false`.

Firebase may throw `auth/account-exists-with-different-credential` when one email belongs to another Firebase sign-in method. VYBE asks the user to sign in using the existing method and then connect the new provider from **Profile → Connect Google or GitHub sign-in**. It does not inspect sign-in methods by email; Firebase's email-enumeration protection can make that lookup empty. It never merges a SQL account based only on social email. A SQL email owned by another UID returns `409 IDENTITY_CONFLICT` and requires the operator ownership process in the [Phase 2A/2B runbook](firebase-phase-2a.md). `auth/credential-already-in-use` also requires support review rather than an automatic Firebase merge.

## Browser flows

On Login or Register, choose Google or GitHub. Existing Firebase UIDs mapped to SQL receive a rotated Laravel session and normal verified, restricted, banned and administrator access behavior. New UIDs go to `/auth/social/username`; the Firebase user remains in memory while Core validates the username. A taken or reserved username can be corrected without another popup. After browser refresh, restart provider sign-in to resume onboarding. The five-minute recent-authentication rule also requires a fresh popup if onboarding takes too long. Successful registration clears Firebase browser state and routes unverified users to the verification screen.

Provider linking requires an existing, verified VYBE session and fresh sign-in to the **same** Firebase UID through the current email/password, Google, or GitHub method. Core checks the signed ID token against the session UID at `POST /auth/firebase/link/authorize`; a different UID receives `403 IDENTITY_MISMATCH`. The browser then calls Firebase `linkWithPopup` for the additional provider. This modifies the Firebase identity, not the SQL primary key or VYBE role. Temporary Firebase state is cleared after success or cancellation. A provider attached to another Firebase UID is never merged. The operator-only `vybe:firebase-link` command separately links a legacy SQL user to a verified Firebase UID.

Popup closure reports cancellation, popup blocking reports a browser action, provider misconfiguration reports a setup problem, and network failures report temporary unavailability. The SPA keeps Firebase auth in memory and uses no global Firebase listener or routine Firebase polling. Popup authentication on browsers that prohibit popups is a known acceptance limitation; a redirect fallback can be evaluated later without changing Core's contract.

## Manual acceptance

Use dedicated Google and GitHub test identities in the configured Firebase project and a disposable Core database. For each provider: sign in as a new user, confirm no SQL row exists at `202 USERNAME_REQUIRED`, choose a valid username, confirm one UID/SQL mapping and Laravel session, reload, access a protected route if Firebase reports verified email, and log out. Repeat with an existing mapped UID and confirm its numeric ID, username, role and activity remain unchanged. Test an unverified provider email against the verification screen; test a GitHub account with no usable email and confirm `EMAIL_REQUIRED` without a local user. Test SQL email collision, Firebase different-credential conflict, popup cancellation/blocking, banned/restricted/admin accounts, session persistence and logout. From a verified existing account, confirm the current Firebase method, connect the other provider, then sign in through both methods and confirm the same SQL ID. Check CSRF rejection and 429 throttling in a safe test environment.

Automated tests fake Firebase SDK/provider HTTP; they are not browser OAuth acceptance. This phase adds no migration and does not change Movie Catalog or administrator password/invitation flows. Phase 2D still needs Firebase-aware administrator account management.
