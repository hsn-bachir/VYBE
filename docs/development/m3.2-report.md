## Database changes

`2026_11_06_000001_add_review_moderation_and_reports.php` adds `reviews.visibility` (`visible` by default) and `reviews.moderator_spoiler` (`false` by default), plus public/moderator listing indexes. It creates `reports` with nullable `reporter_id` and `resolved_by` user foreign keys using `ON DELETE SET NULL`, a logical review target, reason, optional description, status, resolution fields and timestamps. A unique `(reporter_id, target_type, target_id)` index enforces one report per reporter and review; status/date and target indexes support bounded queues. MySQL CHECK constraints bound visibility, target type, reason and status; request validation provides the same API boundary on SQLite. Rollback removes the report table and new review fields without deleting reviews.

The `Report` model owns explicit mass-assignment fields and user/review relationships. `Review` casts `moderator_spoiler`; `User` has a reports relationship. Public reviews remain published by default. Public review lists and counts apply `visibility = visible` in SQL before pagination. Hidden reviews remain available to their authors for edit/delete and to moderators through privileged endpoints. An effective spoiler flag is the author flag OR moderator flag; author edits do not clear moderator enforcement.

## API, authorization and audit

- `POST /api/v1/movies/{tmdb_id}/reviews/{review_id}/reports`: verified active session, CSRF, canonical IDs, allowed reason, at most 1,000 Unicode characters of description, no unknown fields, no self-reporting, visible matching target. Returns 201 for a new report or 200 for the unchanged original. Missing, hidden and mismatched targets return 404. Limits: five/hour/user and twenty/hour/IP.
- `GET /api/v1/admin/reports` and `GET /api/v1/admin/reports/{id}`: bounded status queue and full report inspection for moderators/admins, including restricted privileged readers. Deleted target and deleted user references have safe projections.
- `POST /api/v1/admin/reports/{id}/resolve` and `/dismiss`: active privileged writes with required reason. Resolve hides the review or enforces spoiler protection; dismiss leaves the review intact. Repeating the same completed decision returns the original result without another audit row. Incompatible transitions and unavailable targets return safe conflicts; deleted-target reports can be dismissed.
- `GET /api/v1/admin/reviews`, `PUT /api/v1/admin/reviews/{id}/visibility`, and `PUT /api/v1/admin/reviews/{id}/spoiler`: bounded review management and direct reasoned hide/restore or moderator spoiler changes. Unchanged direct updates create no audit row.
- `GET /api/v1/admin/actions`: bounded history. Moderator reads are limited to review/report moderation action types; administrator reads retain the broader M3.1 history.

All privileged routes use existing role/state middleware, private no-store responses and admin read/write throttles. Mutation services lock and recheck the actor, then target review and report in a consistent order. Review/report changes and `AdministrativeAction` records commit in one Core transaction. Audit details contain bounded action and ID data, never report text, review body or credentials. Database uniqueness settles duplicate reports. The report controller does not contact Catalog; Core review identity is authoritative.

## Frontend and interaction

Movie Details adds a Report action only for a verified, active non-author. Its shared-dialog form has explicit reasons, optional details, field errors, pending state and separate new/duplicate feedback; it explains that a report does not automatically remove a review. `/admin/reports`, `/admin/reports/:id`, `/admin/reviews` and `/admin/actions` are lazy protected routes. The admin shell shows moderation tools to moderators and administrators and keeps user management administrator-only. Report investigation and direct review changes use a reason-confirmation dialog. Restricted privileged accounts can inspect but cannot act.

Private moderation query keys are `['admin', ownerId, 'reports'|'report'|'reviews'|'actions', …]`; reads are cancellable and writes do not retry. Confirmed moderation writes invalidate the current owner's admin queries and, when a movie is known, its public and personal review queries. Existing auth-change cache clearing and a post-CSRF owner check prevent a stale account mutation callback from updating another account. The report dialog uses existing VYBE colors and focus-managed Dialog; no animation dependency or separate notification system was added. The report dialog action spacing is defined locally so it remains correct when Movie Details has not loaded administrator CSS. Child moderation pages consume the verified access context from `RequireAdmin`, avoiding an extra access refetch and route remount loop.

## Deployment and remaining limits

Deploy the Core migration before the new API and frontend. No Catalog migration or service change is required. Existing Core session/CSRF, role and account-state configuration remains in use. Hosted CI and human review have not run. The browser journey used API fixtures, so a real browser-to-disposable-Core end-to-end journey and truly concurrent MySQL transactions remain unverified. The schema and transactions enforce duplicate and transition integrity, but concurrency under simultaneous independent connections should be exercised before release. Report/audit retention and hard account deletion still require the product decision noted in the milestone checklist. M3.3 recommendations are not implemented.
