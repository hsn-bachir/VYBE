## Implementation and design

- The detail page replaces only Participants with a host row and organizer-only paginated invitation roster. Pending, Accepted and Declined labels are explicit, with server-provided response timestamps. The host is separate from invitation records. Accepted guests see the host and a guest-list privacy explanation; their component never mounts the roster query.
- Eligible hosts can open the shared accessible Dialog and search normalized username prefixes after a 350 ms debounce. Search validates ASCII letters/digits/underscores, 3–30 characters after trimming/lowercasing. Prefix/page keys isolate responses; old-prefix results disappear immediately during editing, before the next request. Search and roster each request 12 records per server page. No global relationship/RSVP totals are inferred.
- Search supports loading, no matches, independent pagination and explicit retry. Invitation 422 field errors are displayed. Duplicate submissions are blocked synchronously and while pending; successful authoritative target IDs stay locked for the dialog lifetime while refreshed eligibility removes them. Core determines eligibility, including self/already-invited exclusion. Success refreshes only the affected event's roster/search queries, preserving unrelated event requests and mutations. No roster entries are synthesized locally.
- Inbox and My nights cards support pending accept/decline, accepted-to-declined and declined-to-accepted. Accepted detail has the same RSVP control. Existing URL view/status/page state survives card declines. Responded invitations remain in the separately paginated inbox. There is no withdrawal or pending-state restoration.
- Accepted decline opens a safe-default confirmation explaining private-access loss, existing vote removal and no automatic vote restoration on reacceptance. Dialogs reuse shared focus trapping, Escape handling, trigger restoration and semantic tokens. Long names wrap; buttons, roster and cards remain in normal layout flow. Existing reduced-motion behavior is preserved. Shared shortlist and Voting remain placeholders.

## Permissions, privacy and reconciliation

| Surface/action | Boundary |
| --- | --- |
| Full participant roster | Verified active/restricted organizer only; retained read-only after start/cancellation/finalization |
| Send invitations | Central `invite` permission: active verified host, scheduled/open event, before start; Core rechecks |
| Change RSVP | Active verified invitee, scheduled event, strictly before start; no organizer RSVP controls |
| Pending/declined summary | Common title/host/schedule/status only; no private detail request or private link |
| Accepted private detail | Fresh authorized Core GET after server-confirmed acceptance; never assembled from summary data |
| Successful decline | Approved synchronous event/list/inbox purge removes detail, shortlist, votes, roster and rich projections before navigation/refetch |

The M5.7.2 RSVP mutation intentionally resets mounted Mutation Observers during its purge. UI completion awaits `mutateAsync` directly rather than observer data or per-call `onSuccess`. A session-only completion context survives the intentional event-generation change while still rejecting logout/account switch/account-wide revocation. The source-review correction below additionally retires completion presentation and navigation on external permission loss or originating-component unmount; an imperative confirmed-write receipt identifies the successful mutation’s own purge. Navigation is also limited to the originating URL; leaving a page cannot trigger a later redirect back. Acceptance navigates to the newly mounted detail query. Detail decline immediately returns to the minimal inbox; card decline requests a fresh projection for the unchanged selected view/page/filter. Background refetch is not awaited before hiding private content.

No private query DTOs are copied to independent component state. Local state holds input text, pagination, error/status copy, confirmation selection, submission locks and server-confirmed invitation target locks. Private detail and roster remain in Query. Permission loss unmounts dialogs and clears their drafts/results; render-time selection clearing prevents automatic reopening after restoration. Session/event boundaries protect mounted consumers and delayed responses. Host/accepted membership checks, AbortSignals, disabled mutation retries, terminal lifecycle protection and M5.7.3B ambiguous-edit reconciliation are preserved.

401/403/404 follow existing guarded-request revocation rules; event denials purge the affected event and mixed projections without revoking unrelated events. Failed RSVP does not optimistically change membership or purge valid private data. 409 refreshes authoritative state; client clocks remain advisory and never decide server permission or vote/winner state.

## Targeted source-review correction — RSVP presentation lifetime

The operator identified that an RSVP component could stay mounted across permission changes, retaining its prior error and local busy state. Its promise continuation checked session/URL but did not remember that the originating presentation had lost permission. Merely clearing confirmation did not retire that continuation.

Correction scope is five existing slice files: `components/MovieNightRsvp.tsx`, `hooks/useMovieNights.ts`, `tests/invitations.test.tsx`, `frontend/tests/movie-night-invitations.browser.mjs` and this report. Other slice changes in the inventory above are preserved without additional edits in this pass.

- Both permission-loss and permission-restoration transitions reset local error, confirmation and submission presentation. An independent per-attempt completion token is irreversibly retired when external permissions disappear; restoring permission never restores that token or previous messages.
- The actual command lock and installed Query mutation pending state survive presentation cleanup until settlement, blocking duplicate requests. Delayed failure cannot set retired local state. Leaving the originating component retires navigation even when browser Back returns to the identical URL.
- An optional imperative receipt is marked only after a current, successful RSVP adapter response and immediately before the existing synchronous purge. This distinguishes the command's own intentional event-generation revocation/unmount from an external permission loss. It does not modify API contracts, cache generations or authorization. The normal accepted/declined/reaccepted workflows retain fresh authorized reads and immediate purge/navigation.
- A server-confirmed write always retains existing private-cache reconciliation. Independently of whether its old UI may display completion, a same-session currently visible dashboard requests its exact current server descriptor. A retired private detail remains unavailable after confirmed decline; it cannot regain private content or redirect on restoration. Account/session guards still reject cross-account completions. Failed writes preserve membership.
