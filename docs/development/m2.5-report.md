## C. Backend API

All profile routes are private, session-authenticated, verified, CSRF-protected for writes and no-store. Ownership comes only from the session.

| Endpoint under /api/v1 | Result |
| --- | --- |
| GET `/me/profile` | 200 profile envelope |
| PATCH `/me/profile` | 200 updated envelope; username and/or bio only |
| POST `/me/profile/avatar` | 200 updated envelope; multipart avatar only |
| DELETE `/me/profile/avatar` | 200 updated envelope, null avatar; repeated removal also succeeds |

ProfileResource wraps the existing exact five-field UserResource under data.user and adds bio, member_since, and statistics with watched_count/watchlist_count/review_count. `/auth/me` gains no fields. Public authors still contain only id/username/avatar_url, never email or biography.

UsernameRules is shared with registration: trim/lowercase, 3–30 ASCII letters/numbers/underscores, existing reserved names and database uniqueness. Update ignores the authenticated ID; a final uniqueness conflict becomes standard username 422. Bio trims Unicode edges, preserves internal whitespace/newlines, accepts null or up to 500 code points, and normalizes blank to null. Literal text is escaped in React, without HTML/Markdown interpretation. Empty PATCH, non-JSON edits, unsupported fields and query parameters are rejected. Email/password/verification/avatar_url/owner changes are forbidden through PATCH.

ProfileService locks the current user for edits, assigns only supplied fields and preserves sessions/unrelated attributes. Reads refresh the user, then loadCount executes one aggregate query with three indexed subqueries. It does not load relationship arrays or call Catalog. Counts reflect committed rows, including zeros, and exclude other users.

GET shares library-read 120/minute/user; writes share library-write 60/minute/user. Upload additionally uses avatar-upload 5/minute/user; removal is still available when the upload limit is exhausted. Safe JSON 401/403/404/413/419/422/429/500/503 handling preserves private no-store and Retry-After where applicable. Debug responses do not expose SQL or storage paths.

## D. Avatar security

Core's existing public disk stores only generated `avatars/{owner}/{32-random-hex}.webp` files. Uploaded names and paths are ignored as identity; no arbitrary URL or storage path can be submitted. The database stores `/avatars/...`; API URLs use trusted APP_URL, not the request Host.

Laravel validates actual file content/MIME, at most 2 MiB, and dimensions 1–2048 on each side before decoding. JPEG, PNG and WebP are supported; SVG/GIF/corrupt/fake/oversized files are rejected. AvatarService verifies bounds/MIME again, decodes with GD, normalizes JPEG EXIF rotations/mirrors, resizes proportionally to at most 512px per side and emits fresh WebP at quality 85. Original bytes/metadata are not published. Tests cover all eight orientation values, a metadata marker, minimum dimensions and aspect-preserving bounds.

Processing/storage happen before a short user-row transaction. Replacement re-reads and locks the user, saves the new reference, commits, then removes only the old exact managed path matching that owner. Database failure attempts deletion of the new unreferenced file and preserves the previous reference. Removal locks/clears first, then cleans the previous path; absent avatars are ordinary success. Random references are never reused, so concurrent operations cannot make an obsolete cleanup target current again. Parallel worker checks produced two successful replacements with exactly one remaining current file. Legacy URLs, foreign directories and traversal-like references are never deleted.

Failed obsolete-file cleanup logs only user ID and does not undo committed identity. A process crash between storage/commit/cleanup can leave an orphan; automatic housekeeping is not introduced in this slice. Storage/processing unavailability returns safe 503 AVATAR_UNAVAILABLE. Existing confirmed avatars remain visible on failed writes.

Auxiliary public GET `/avatars/{owner}/{32-hex}.webp` streams only the constrained public-disk path, without a browser session or profile projection. Successful assets use image/webp, X-Content-Type-Options:nosniff, restrictive CSP and immutable public caching. Missing files return an empty 404. This route requires no general storage symlink or new media service.

Deployment requires persistent writable Core storage/app/public, backups coordinated with database references, canonical HTTPS APP_URL and proxy routing of /avatars/* to Core. Enable GD JPEG/PNG/WebP and EXIF, then restart PHP workers. The bundled local extensions were enabled in `C:\src\php\php\php.ini`; a pre-change backup is in the user's temporary directory. Core CI now declares GD/EXIF. Normal Core/Catalog workers were restarted after the change. PHP/proxy request limits must allow 2 MiB plus multipart overhead; application limits remain authoritative. Production PHP display_errors must be off.

## E. Frontend

Lazy `/profile` uses RequireAuth and AppLayout. It presents identity/avatar/bio/member date, real movie-journey counts, owner-only read-only email/verification, avatar controls and Watchlist/Watched/Collections links. Reviews is a non-clickable count; no invented review-history route. Empty bio and zero activity have deliberate states; failed reads offer retry, cached refreshes show status instead of fabricated emptiness.

ProfileEditor reuses native Dialog, prefilled controlled fields, Unicode counts, inline validation, pending protection and focus containment/restoration. Failed requests retain inputs. Closing keeps the draft while the page remains mounted, with explicit feedback; confirmed save clears it. Account changes reset owner-keyed local state. Drafts are not persisted across navigation/reload.

AvatarEditor labels a local selection as Preview/not saved; the confirmed avatar remains separate. File-type/size checks give immediate feedback; server validation remains authoritative. Failed upload preserves the preview and confirmed avatar for retry. Object URLs are revoked on replacement/discard/unmount/success. Upload and removal clear previous success feedback before dispatch, preventing an older confirmation from describing the new request. A shared Avatar supplies safe image rendering and initials after missing/failed images in navigation, Profile and review cards.

Numeric query keys: `['me',owner,'profile']`; mutation `['me',owner,'profile-write']`, serialized per owner. Reads forward AbortSignal, staleTime 30 seconds, retry false and no focus polling. Mutations bootstrap CSRF, check current verified identity before dispatch and again before/after cancellation, then update existing authKey and profile from server responses. Public review pages and personal review-author projections are invalidated; metadata, discovery, ratings and Library caches are untouched. Library membership and review writes invalidate the owner's cached profile for counts. Existing auth cancellation/clearing prevents cross-account data; 401/403 clear affected profile state and refresh auth. No automatic write retry or optimistic saved state.

## I. Known limitations

Production persistent storage/permissions/backups, canonical HTTPS origin, proxy/upload settings and PHP GD/EXIF capability require deployment verification. Public images may remain in downstream caches after removal; clearing a profile/reference/file cannot revoke cached public copies. Obsolete-file cleanup is best effort, with logged failures and potential crash orphans; no job infrastructure is added. Legacy avatar URLs are not imported or deleted.

Hosted CI/human PR review, production/CDN hosting, live TMDB/email/YouTube, MariaDB, full screen-reader/device-lab coverage and release were not verified. Browser accessibility snapshots/keyboard/screenshots are local evidence. Normal local writes were not made to a real user's profile; all write journeys used isolated test accounts/storage. M2.5 has no public profile, following, activity feed, email/password/account deletion, OAuth linking or profile-completion system.
