# M3.1B engineering report — administrator user management

Date: 2026-11-04. Branch: `feature/roles` at `d4a4707` when work began. The completed M3.1A foundation was already present locally as uncommitted files; this slice builds on and preserves it. No commit, branch change, merge, push or PR was made.

## Repository findings and implementation

Core already owned user accounts, Sanctum stateful sessions, email verification, `EnsureAccountAccess` current-state checks, `EnsureRole`, role gates, and trusted initial administrator provisioning. React already had `/admin`, `useAccess`, shared Axios/CSRF, dialogs, semantic tokens and account-scoped query conventions. M3.1B extends those foundations with private administrator user management. Catalog and the movie database were not changed.

## Database and audit

`AdministrativeAction` belongs to its actor, and `User` has many performed administrative actions. The target ID remains a logical reference.

`2026_11_03_000005_create_administrative_actions_table.php` adds an auto-increment `administrative_actions` table in Core. `actor_id` references users and becomes null if an account is deleted; `target_type`/`target_id` are a logical reference. Indexes support target and actor history in timestamp/ID order. The `AdministrativeAction` model casts only approved JSON details and the timestamp. The service writes `user.updated`, `user.role_changed`, or `user.status_changed` only after an actual change. Identity edits record changed-field booleans; role/status changes record old/new values and a trimmed reason. Email, password, tokens, sessions and request bodies never enter details. No audit API or application update/delete behavior exists. A retention period remains undecided.

## API contract and security

The write lock set is bounded to active administrator rows by the existing `(account_status, role, id)` index; an inactive administrator target is locked separately.

Implemented Core routes: `GET /api/v1/admin/users`, `GET /api/v1/admin/users/{id}`, `PATCH /api/v1/admin/users/{id}`, `PUT /api/v1/admin/users/{id}/role`, and `PUT /api/v1/admin/users/{id}/status`. Responses use the dedicated eight-field `AdminUserResource` and private no-store headers. The list has bounded `page`/`per_page`, exact normalized email/username or indexed username-prefix search, role/status filters and `id ASC` ordering. Requests reject unknown fields and noncanonical IDs; PATCH accepts username/email only. Active or restricted verified administrators may read; only active verified administrators may mutate. Reads are limited to 60/minute/actor and 120/minute/IP; writes to 20/minute/actor and 60/minute/IP. Existing Sanctum session/CSRF and safe JSON errors are retained.

The write service locks administrator rows in ID order, locks a nonadministrator target if needed, and rechecks the acting administrator after the lock. It protects self role/status changes and the last verified active administrator. A changed email clears verification. The last verified active administrator cannot change email; another administrator changing their own email is signed out after the transaction and must verify the new address. User change, session deletion and audit insert share one Core transaction. The default database session driver uses the Core connection, so affected sessions are deleted transactionally. For another session driver or separate session connection, deletion is not atomic and the live account/role checks remain the server authority. This project currently uses Sanctum web sessions and has no personal API token implementation. Duplicate username/email errors are 422; prohibited transitions are 409. The M3.1A restrictions on community writes and review visibility remain intact.

## Frontend and UX

An admin API 401/403 clears the current owner's admin cache and refreshes auth/access as appropriate, so stale private data is not retained after session or role changes.

`/admin` links administrators to lazy `/admin/users` and `/admin/users/:id`; moderators see no user-management link or screen. The list has URL-backed server pagination, a delayed search, role/status filters and responsive mobile cards. Details show account identity and status with edit, role and status dialogs. Status changes explain their effect and require a reason; errors preserve form input and confirmed state. The shared Dialog traps/restores focus and supports Escape. Styling uses VYBE tokens with no new UI dependency or decorative animation. Queries use `['admin', ownerId, 'users', filters]` and `['admin', ownerId, 'user', targetId]`, forward AbortSignal, and invalidate only this owner's admin data after success. Self edits refresh auth/access. The existing login/logout private-cache cleanup remains in use; pending writes check the owner again after CSRF bootstrap and before success feedback.
