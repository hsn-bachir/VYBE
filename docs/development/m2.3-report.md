## B. Database

New Core migration: `2026_11_03_000001_create_movie_ratings_table.php`.

- `id`, `user_id`, `tmdb_id`, unsigned tiny integer `rating`, Laravel timestamps on MySQL.
- Core user FK with cascade deletion; unique `(user_id, tmdb_id)`; statistics index `(tmdb_id, rating)`.
- Enforced CHECKs for rating 1–5 and canonical TMDB range 1–2147483647. MySQL 8.0.43 verified; require CHECK enforcement (MySQL 8.0.16+). MariaDB was not exercised in this slice.
- SQLite declares its checks/FK during CREATE TABLE and adds the equivalent indexes. Its rating check also requires stored integer type. API validation stays strict independently of database numeric coercion.
- `MovieRating` permits only tmdb_id/rating mass assignment, casts both to integers, and belongs to User. `User::movieRatings()` scopes ownership. No movie metadata, Catalog FK, review ID, rating history or library relationship.

Migration rollback/reapply passed on separate disposable SQLite and MySQL databases, dropping only movie_ratings. Range, uniqueness, indexes and user deletion cascades passed on both engines. The existing additive migration was also applied to the normal local `vybe_core` database after isolated verification, without resetting or deleting existing application data.

## C. Backend

| Endpoint under `/api/v1` | Behavior |
| --- | --- |
| GET `/movies/{tmdb_id}/ratings` | Guest-readable 200; VYBE average/count/all five string-keyed distribution buckets |
| GET `/me/ratings/{tmdb_id}` | Verified owner only; 200 personal projection or `data: null` |
| PUT `/me/ratings/{tmdb_id}` | Verified owner only; strict JSON integer 1–5; create/replace returns 200 |
| DELETE `/me/ratings/{tmdb_id}` | Verified owner only; 204 including absent rating |

`RatingRequest` reuses canonical movie route validation, rejects unsupported fields/query parameters and form submissions, and rejects decimal JSON (including 5.0), strings, booleans, null, arrays/objects and out-of-range values. Ownership comes from the authenticated session. `MovieRatingResource` exposes only tmdb_id/rating/updated_at. PUT CORS is enabled. Private operations share 120 reads and 60 writes/minute/user with Library; public community reads use 120/minute/IP. No-store and sanitized 419/429/500 responses preserve Retry-After and do not expose SQL/provider internals.

`RatingService` checks for an existing personal rating first. New references use shared Catalog confirmation; cache miss is unresolved 422, never a manufactured TMDB 404; unavailable Catalog yields safe 503. Existing reads/updates/deletion and public statistics make no Catalog request.

Writes use atomic upsert under the unique owner/movie key, then read the result in the same short local transaction. There is no HTTP inside it. Last database writer wins; ID/created_at persist, and updated_at may advance on an identical PUT. Three transaction attempts handle deadlocks; the browser does not automatically retry writes. Concurrent create and conflicting update workers synchronized before SQL produced one row and a later PUT replaced it. Deletion affects only the authenticated owner's rating.

Statistics use exactly one grouped SQL query. Zero-filled buckets supply the count and weighted average, rounded half-up to two decimal places as a JSON number; trailing zeros are presentation-only. No ratings gives null average, total zero and five zero buckets. No aggregate cache/table/job or Catalog dependency.

## D. Frontend

New `features/ratings` contains typed DTO/API methods, query/mutation hooks, CommunityRatingSection, RatingHistogram, CSS and focused tests. The lazy section sits after Cast and before related movies, preserving Details and its existing Library actions. VYBE average is formatted to two decimal places on a 1–5 scale; the hero TMDB score remains on 0–10. Five accessible histogram rows show exact counts and rounded percentages; empty, loading, partial refresh and retry states are explicit.

Query keys use numeric IDs:

- Public: `['movies', 'ratings', tmdbId]`.
- Personal: `['me', userId, 'rating', tmdbId]`.
- Mutation: `['me', userId, 'rating-write', tmdbId]`.

Reads forward AbortSignal, use 30-second staleTime, no automatic retries/focus polling. Private queries mount after verified authentication. PUT/DELETE bootstrap CSRF and verify the current account before dispatch. Mutation scope serializes a user/movie; pending disables conflicting controls. Successful responses cancel old matching reads, check identity again, set confirmed personal data and invalidate only personal state plus matching public statistics. Library, collections, discovery and metadata caches are untouched. Existing login/logout cancel/clear behavior applies; 401/403 remove affected private state and recheck auth. Late-account callback guards are unit tested, and actual two-user browser sessions verified isolation.

Failures retain the last confirmed rating, display persistent contextual feedback, and allow explicit retry. Statistics are never optimistically fabricated. A statistics refresh failure preserves the prior public data and does not undo a confirmed personal save.

## H. Known limitations and deployment

- Hosted CI/human review, live TMDB/email delivery/YouTube playback, full screen-reader/device-lab acceptance and MariaDB-specific enforcement were not verified. Existing fake-provider suites cover unchanged boundaries.
- A fresh Movie Details load still needs Catalog for its base movie metadata. The already-loaded rating section and rating APIs remain usable during an outage; M2.3 does not create a second movie cache in Core/browser storage.
- Other users/tabs see aggregate changes on refetch/stale-time use, not push. No polling/WebSockets or optimistic aggregates. Percentages can round to a total other than 100; exact counts remain visible.
- Apply `cd backend && php artisan migrate` before deploying the new Core/frontend. CHECK-enforcing MySQL is required. Refresh cached CORS config for PUT if used. No Catalog migration, new environment variable, secret or dependency. Rollback deletes ratings and needs a deliberate retention decision outside disposable tests.
- Normal local migration was applied and localhost Core/Catalog/Vite were started for use. The normal frontend, ratings API and base movie details returned 200; the guest community section/sign-in action rendered correctly. Expected guest auth checks return 401. Disposable test services/MySQL were shut down after verification, with the normal app left running. Local readiness is distinct from deployment/CI acceptance.
