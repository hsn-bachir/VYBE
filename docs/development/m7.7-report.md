Work started on the clean `feature/m7-admin-security-finalization` branch at `2921cdd`. M7.1–M7.6 are already merged into `dev` through PRs #35–#37. This implements the three administration audit findings for PDF objective 11. No branch switch, commit, push, merge or PR was performed.

## Implemented fixes

### F1 — Administrator email changes

Core deliberately rejects Firebase email changes targeting **any administrator**, regardless of administrator count, with `409 ADMIN_EMAIL_CHANGE_UNAVAILABLE`. After the existing fresh same-UID confirmation, `FirebaseAdminUserService::email` checks the locked current target before session revocation, intent audit or Firebase mutation. Thus two administrator email attempts cannot both clear verification, and a concurrent administrator status change cannot expose the old remote-write window. If actor access is revoked first, existing live authorization can instead return 403. No additional locks are held across remote requests and no cross-system atomicity is assumed.

Administrator username-only editing and unchanged email values remain available. Non-admin email editing preserves collision checks, early committed session revocation, requested/completed audits, verification clearing and retry after Firebase/SQL partial failure. Legacy-mode email handling retains its existing last-administrator safeguard. Rejected administrator changes leave SQL identity, verification, session version and audit rows unchanged; the confirmation remains one-use.

### F2 — Session revocation

`AdminUserService::revokeSessions` now rotates the existing `password_session_version` and remember token. The same SQL transaction contains the role/status mutation, revocation and audit. Compatible database sessions are still deleted. Existing middleware rejects retained sessions on file/database drivers; restoration generates a further version and never restores an old session. Fresh login/session exchange uses the existing version-binding behavior. No-op role/status transitions do not revoke sessions. Failed audit writes roll back role/status, version, remember token and database-session cleanup together.

Legacy password changes reuse the same helper without double rotation. Existing legacy email changes also receive driver-independent revocation; changed-field audit booleans are captured before the helper saves the user again. Firebase credential operations retain their own existing early revocation/recovery path.

### F3 — Refresh outcomes

Core continues to persist intent before calling Catalog and updates that same row:

| Action | Meaning |
| --- | --- |
| `movie.refreshed` | Validated refreshed DTO, fresh metadata status and full-fetch timestamp. |
| `movie.refresh_failed` | No dispatch because configuration is invalid, Catalog 409 lock/cooldown rejection, or structured pre-write provider `404 MOVIE_NOT_FOUND` / `503 UPSTREAM_UNAVAILABLE`. |
| `movie.refresh_unconfirmed` | Timeout/connection loss, generic or unrecognized response, invalid success DTO or another exception that does not establish whether Catalog committed. |
| `movie.refresh_requested` | Intent remains incomplete after interruption or failed audit completion. |

The existing Catalog force-refresh path emits the recognized provider errors before the metadata upsert and swallows optional post-write `UpstreamUnavailable`. Core conservatively leaves unrecognized errors uncertain. `CatalogFailure` adds internal classification only; browser HTTP statuses/messages remain unchanged and contain no internal exception details. History has explicit unconfirmed/incomplete labels. The existing action column/resource allow these strings without migration. Historical failed rows retain their old meaning and are not reclassified.

There are no new provider calls, automatic retries, queues or reconciliation workers. An administrator can inspect current metadata/timestamp and explicitly retry after the existing cooldown. Catalog code and its refresh protections are unchanged.

## Requirements and retention

The original `../Web2_CCE_Project.pdf`, page 3 objective 11, requests local movie data management without explicitly specifying full CRUD. M7.6 provides browse, search, inspection, health filters and explicit provider refresh. Manual creation/editing/deletion of provider-owned records remains outside this scope; instructor confirmation of this interpretation remains open.

Administrators can deactivate accounts. Deactivation denies access while retaining related data and Firebase identity; it is not deletion. Hard deletion is not implemented and requires a separately approved retention/privacy/Firebase identity policy that accounts for cascading personal data and retained reports/audits. MFA is optional future scope.
