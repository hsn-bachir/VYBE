# Firebase authentication: Phase 2A and 2B

## Configuration and the Phase 2A failure

Core uses `AUTH_IDENTITY_PROVIDER=firebase`, `FIREBASE_PROJECT_ID`, and `FIREBASE_CREDENTIALS`; the SPA uses the matching `VITE_AUTH_IDENTITY_PROVIDER=firebase`, `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, and `VITE_FIREBASE_APP_ID`. Install the committed Composer/npm lockfiles and run only the additive Core migration. Keep the service-account JSON outside the repository. `legacy` remains the default mode until coordinated cutover.

The observed local 503 occurred before ID-token verification: Kreait Laravel's credential-path resolver treated a `C:/...` value of `FIREBASE_CREDENTIALS` as a relative path on Windows. Use a native absolute Windows path such as `C:\secure\firebase-service-account.json` in local `backend/.env`, ensure the file is readable, and clear cached configuration if enabled. A second live defect caused 401 after the path correction: Kreait's verified token exposes `aud` as an array, while Core compared it with a string. Core now accepts only the single expected project audience. Do not disable TLS or revocation verification. Core logs only failure stage and exception class. Check `php artisan migrate:status`, MySQL connectivity, matching project IDs, PHP curl/OpenSSL and the configured CA bundle if login still fails.

Enable Firebase email/password sign-in and add the SPA host to Firebase Authentication Authorized domains. In Authentication Templates, set the project's **custom action URL** to `<FRONTEND_URL>/auth/action`; Firebase uses this one handler URL for all email templates. The `url` action-code setting in API calls is a safe `continueUrl`, not the handler URL. The SPA handler dispatches `verifyEmail`, `recoverEmail`, and `resetPassword` by Firebase's `mode` parameter. See [Firebase custom email handlers](https://firebase.google.com/docs/auth/custom-email-handler) and [continue URLs](https://firebase.google.com/docs/auth/web/passing-state-in-email-actions).

## Browser and session flow

Registration collects username/email/password/confirmation. Firebase creates the identity and returns an ID token. Core verifies the token and current Firebase record, validates the username, creates a SQL user with `firebase_uid` and null password, and rotates a Laravel session. The browser requests a verification email and clears temporary Firebase state. If SQL validation fails after Firebase creation, the in-memory identity can retry with a corrected username. After a reload, the user can sign in with the new Firebase credentials; session exchange can provision a local user with a generated username. A colliding local email returns `409 IDENTITY_CONFLICT` and requires explicit linking.

Sign-in exchanges a fresh Firebase ID token once. Core validates signature, audience, issuer, authentication time, revocation, disabled state, and current UID/email. Subsequent requests use the Laravel/Sanctum cookie only. Core does not call Firebase for ordinary browsing or `/auth/me`. Firebase mode rejects local-only sessions and legacy login/registration/password/invitation writes. Laravel roles, account statuses, verification gate, moderation and logout remain in force. Banned/deactivated users can establish a session but receive the existing 403 on `/auth/me`; restricted users keep their existing read/write limits.

Firebase email verification is authoritative. The email action page applies the one-time code without a Firebase `currentUser`, including in a different tab or browser. A signed-in browser then calls `GET /auth/email/verification-status`; Core fetches the trusted Firebase record and updates local `email_verified_at`. A browser without a Laravel session signs in before synchronization. Resend uses the server-side Firebase SDK and linked UID. Invalid/expired codes show a retry path. Only identity screens request a Firebase status refresh.

Forgot password sends Firebase's templated email through Core with a generic response for unknown addresses. The action page checks the code, then submits the code and new password to Core. Core verifies the code and calls Firebase to change the password and revoke Firebase refresh tokens; Core never stores the new password. Before consuming the one-use code, Core rotates the linked user's local session version and deletes database-backed sessions on the same connection. A failed confirmation can require sign-in again; a successful reset cannot leave prior Laravel sessions usable. Other session stores rely on the version check at the next protected request. Invalid/expired codes return 422.

## Existing users and email changes

Do not link by email alone. An operator may run `php artisan vybe:firebase-link <local_user_id> <firebase_uid>` after independently confirming account ownership. The command requires an enabled, email-verified Firebase identity whose normalized email matches the unlinked SQL user. It preserves numeric ID, role, status, profile and relationships, and rotates the local session version. Browser clients cannot call it.

On a Firebase identity refresh, Core synchronizes mapped email and verification truth. An email change rotates the local session version and clears old verification before setting trusted current status. If another local account owns the new email, Core returns `409 IDENTITY_CONFLICT`, leaves email ownership unchanged, clears local verification, and invalidates old sessions. An external email change becomes visible at the next sign-in or explicit verification-status check, since browsing does not poll Firebase.

## Postman session flow

1. In a private Postman environment, call `POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key={{firebase_api_key}}` with `{ "email":"<Firebase email>", "password":"<Firebase password>", "returnSecureToken":true }`. Keep `idToken` temporary; never share it. The password goes to Firebase, not Core.
2. With one Core host and cookie jar, call `GET {{core_url}}/sanctum/csrf-cookie`. Decode the `XSRF-TOKEN` cookie and pass it as `X-XSRF-TOKEN` on writes. Keep the Laravel session cookie.
3. Within five minutes, call `POST {{core_url}}/api/v1/auth/firebase/session` with `Accept: application/json` and `{ "id_token":"<temporary ID token>" }`. The response is the normal User DTO and a rotated Laravel session cookie. For registration with a selected username, use `/api/v1/auth/firebase/register` with `{ "id_token":"...", "username":"movie_fan" }` instead.
4. Use the cookie for `GET /api/v1/auth/me` and a protected route such as `GET /api/v1/me/access`. An unverified account receives 403 for private access. Call `POST /api/v1/auth/logout` with CSRF and the same cookies; `/auth/me` then returns 401. Clear the temporary token.

Postman verification resend and password-reset requests also need CSRF but no React client. A 419 requires a new CSRF bootstrap and explicit retry. Exchange 401 indicates invalid/expired/revoked/disabled identity; 409 indicates account conflict, 503 indicates Firebase service/configuration failure, and 429 indicates throttling.

## Manual acceptance and scope

Use a dedicated Firebase test account and disposable Core database. Register through the SPA; check one Firebase UID and one SQL user with selected username and null SQL password, a Laravel session, and pending-verification page. Reload and check `/auth/me`. Follow the email link, including from another browser, then check Firebase and Core verification status before a protected route. Resend and test invalid/expired links. Sign out, sign in, reload, access a protected route, and sign out. Request a reset for known/unknown addresses, complete one reset, reject reuse, and confirm old Laravel sessions are denied. Check banned, deactivated, restricted, administrator, duplicate-email and UID-linked accounts. Run the Postman flow above. Record live acceptance separately from mocked automated tests.

Never run `migrate:fresh` or wipe shared Core data. Firebase-mode administrator creation, invitations and password management remain unavailable until Phase 2D; Google/GitHub sign-in belongs to Phase 2C. Final browser/Postman integration and release acceptance remain pending until tested against a configured project and deployed email templates.
