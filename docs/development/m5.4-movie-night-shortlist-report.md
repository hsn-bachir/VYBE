## Exact endpoints and contracts

Base: `/api/v1/me/movie-nights`.

| Method/path | Input | Success |
| --- | --- | --- |
| GET `/{night}/movies` | Optional `page` 1–10000, `per_page` 1–50, default 20 | 200 `{data:[ShortlistEntry],meta:{page,per_page,total_pages,total_results,metadata_unavailable}}` |
| POST `/{night}/movies` | `{tmdb_id}` only, canonical positive integer 1–2147483647 | 201 `{data:ShortlistEntry}` |
| DELETE `/{night}/movies/{movie}` | No fields; `{movie}` is the positive Core candidate ID | 204, no body |

`ShortlistEntry` is exactly `{id,tmdb_id,nominated_by:{id,username,avatar_url},created_at,movie:MovieSummary|null}`. The nomination timestamp is ISO UTC. MovieSummary contains `{tmdb_id,title,overview,poster_path,backdrop_path,release_date,tmdb_rating,tmdb_vote_count}`; provider-only fields are stripped. It is attached to the returned model only after persistence or loaded for the response and is never written to Core.

The shared list includes all event candidates in `id ASC` order, regardless of nominator. SQL pagination and one eager-loaded safe nominator query prevent N+1 relation reads. Unknown input fields, malformed event/candidate IDs and invalid TMDB IDs return 422 before provider calls. Missing/cross-event/repeatedly removed candidates return the same hidden 404 envelope. Successful removal permits a later new nomination while open, with a new candidate ID/nominator. Duplicate nomination is a 409 and never transfers ownership. The existing proposed cap is now enforced at **50 candidates/event**; capacity conflict is 409.

## Permissions and M5.3 privacy

All shortlist paths resolve the private `visibleTo` scope and existing `view` policy: only the host and currently accepted participants have access. Pending, declined, outsider and uninvited administrator users receive hidden 404 before Catalog work. No shortlist data is added to minimal invitation summaries. Listing rechecks fresh account/private eligibility after metadata enrichment; decline during enrichment returns 404 rather than disclosing the page.

Nomination uses existing `nominate`; removal uses existing removable state rules and `removeMovie`. An eligible host may remove any unvoted candidate. An eligible accepted participant may remove only their own unvoted nomination. Another participant's nomination returns 403; any candidate with votes returns 409. Both writes require scheduled state and `now < starts_at`; exactly at start is closed. Authorized users retain read access after cancellation/finalization or start.

Routes inherit `web`, Sanctum session cookies, `EnsureAccountAccess`, `EnsureVerifiedAccount`, `PreventAuthCaching` and the existing library-read/write throttles. Writes additionally use `EnsureActiveAccount`. Restricted verified host/accepted users can read but cannot write. Banned/deactivated/unverified accounts are blocked; pending activation is denied by policy. Firebase mapping, M7 session-version revocation, CSRF and private/no-store error/success conventions remain intact. There is no role bypass. Nominator resources expose no email, Firebase UID, role, account status, bio or credentials.

## Catalog integration and failures

Nomination performs private/open/nomination checks first, then calls existing `MovieCatalogClient::details()` before starting the mutation transaction. The older proposed `LibraryMetadata::confirm()` path was intentionally not used for validation: it only checks cached summaries, so a cache miss does not distinguish an uncached real movie from an invalid ID. Detail validation uses Catalog's established hydration/cache/provider rules, including a valid stale fallback. It is not a guaranteed fresh TMDB lookup.

A successful detail DTO is normalized by the existing client; only its summary projection is returned after insert. A confirmed Catalog `MOVIE_NOT_FOUND` is **404**, while connection timeout, service unavailability and malformed success DTOs are **503 UPSTREAM_UNAVAILABLE**. None creates a nomination. Existing internal transport timeouts, service token, redirect prohibition and no automatic Core retry are unchanged. Duplicate/capacity checks occur after validation under the event lock, so a duplicate request still makes one detail validation call; provider failure can precede duplicate conflict.

**Narrow exception-renderer correction:** the Movie Night branch in `backend/bootstrap/app.php` previously rewrote every 5xx into generic 500 and replaced every 404 with the private-event envelope. It now recognizes `CatalogFailure` within that branch and returns its existing safe `render()` with `Cache-Control: no-store, private`, before generic translation. Thus nomination outages retain 503 and confirmed invalid movie IDs retain 404/MOVIE_NOT_FOUND. Missing/private event and candidate IDs remain hidden 404; unrelated endpoint families are untouched. Feature cases assert exact safe envelopes with debug enabled. A forced SQL insert failure still renders generic 500/INTERNAL_ERROR and rolls back, proving the change does not expose arbitrary diagnostics.

Listing reuses `LibraryMetadata::enrich()` and `MovieCatalogClient::summaries()`:

- One batch request per nonempty page, with no per-candidate detail requests. The maximum 50-row page respects the client's **50 IDs before deduplication** limit; the event cap is also 50.
- Empty and out-of-range pages skip Catalog entirely.
- Missing successful summaries retain candidate IDs with `movie:null` and `metadata_unavailable:false`.
- Batch transport/protocol failure retains candidate IDs with `movie:null` and `metadata_unavailable:true`.
- No missing metadata deletes a nomination or changes shortlist membership. This endpoint does not hydrate batch cache misses.
- Provider requests contain only movie IDs, never event/user/location/RSVP/vote information.

## Transactions, locking and races

Nomination validates externally without mutation locks, then uses a three-attempt transaction:

1. Reload/lock actor with `AccountAccess::lock(..., community:true)`.
2. Lock the private parent event and reauthorize fresh private access (including current RSVP).
3. Recheck scheduled/deadline and `nominate`, then check duplicate and capacity under the event lock.
4. Insert the existing model with server-owned event/nominator IDs and return its safe projection.

Cancellation, decline, deadline or account changes during Catalog validation therefore prevent an unauthorized insert. Nomination adds no target-user lock. The existing `mn_movie_unique(movie_night_id,tmdb_id)` remains the final duplicate safeguard; all compliant application writes take the shared event lock. Direct SQL bypasses domain rules and is unsupported application behavior.

Removal locks actor → private event → event-scoped candidate. It checks state/deadline after candidate-lock acquisition, ownership and vote absence, then deletes in the same retryable transaction. Existing restrictive vote FKs remain the database backstop. Future compliant vote mutations must take the same event lock; no voting path was added. Parent-lock serialization prevents capacity overshoot, duplicate nominations and removal after a committed vote.

Existing M5.2 host/event/target-user lock cycles are not redesigned. New shortlist code preserves actor→event order and acquires no additional user lock after the event; removal only adds the candidate lock. Laravel's existing three-attempt deadlock retry is retained. Exhaustive application-wide deadlock/load/retry-exhaustion tests remain open.

## Independent-process PostgreSQL evidence

Seven cases use real separate PHP/Laravel processes and committed fixtures on the isolated PostgreSQL database. All worker HTTP is faked and stray requests are prohibited. Workers assert zero transaction nesting when Catalog validation runs.

| Case | Observed outcome |
| --- | --- |
| Two actors nominate the same movie while contending on the parent lock | One 201, one 409, one candidate |
| Two distinct nominations compete with 49 existing candidates | One 201, one 409, exactly 50 candidates |
| Participant declines while nomination waits inside fake Catalog I/O | Decline commits through existing service, nomination returns hidden 404, no candidate |
| Host cancels while nomination waits inside fake Catalog I/O | Cancellation commits through existing service, nomination returns 409, no candidate |
| Deadline changes to the worker's exact instant during Catalog validation | Nomination returns 409, no candidate |
| A vote commits before waiting removal resumes | Removal returns 409, candidate and vote retained |
| Host and accepted original nominator remove the same candidate concurrently | One 204, one hidden 404, no candidate |

Lock cases observe workers waiting in `pg_stat_activity` before the controlling transaction commits. Provider-I/O cases use temporary marker files to pause only the fake provider; cancellation/decline can commit while the worker waits, demonstrating no actor/event mutation lock is held during that I/O. The independent deadline case uses a controlled worker clock and changes the fixture start; a separate feature case advances application time to the unchanged event deadline during validation. These are domain-service process tests, not simultaneous browser HTTP requests. Vote insertion is a fixture under the parent lock, not a new vote endpoint.

Parent/worker guards require testing mode, local PostgreSQL, `_test` database, empty DB URL, disposable-test flag and exact port 55433. Independent-process tests additively migrate only the isolated test schema, then remove only their own committed fixtures in FK order. The remaining tests use the existing guarded RefreshDatabase harness. No application/shared database was reset.
