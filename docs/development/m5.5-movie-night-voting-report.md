## Implemented behavior and contracts

Core owns the vote records, authorization and aggregation. The existing Movie Night schema, policy/rules, UTC timestamp concern, uniqueness and composite FK are reused. No migration, dependency, configuration, environment, Catalog or frontend changes are needed. There is no Catalog/TMDB call in either path. Live manual API/browser acceptance is explicitly deferred to M5.7; none was started.

Base: `/api/v1/me/movie-nights`.

| Method/path | Input | Success |
| --- | --- | --- |
| PUT `/{night}/vote` | `{movie_night_movie_id}` only; positive Core candidate ID belonging to the event | 200 `{data:{movie_night_movie_id,updated_at}}` |
| GET `/{night}/votes` | No body/query fields | 200 `{data:{totals,my_vote,total_votes,leaders,voting_open}}` |

Example mutation:

```json
{"movie_night_movie_id":42}
```

Both first cast and subsequent updates/repeats explicitly return 200:

```json
{"data":{"movie_night_movie_id":42,"updated_at":"2027-01-15T18:00:00.000000Z"}}
```

The event and voter are server-scoped. Canonical positive event/candidate IDs follow the existing signed SQL-ID rules up to PHP_INT_MAX. Client voter IDs, counts, timestamps, TMDB IDs in place of a candidate ID, unexpected fields and malformed identifiers return 422. Missing/deleted/cross-event candidates return the standard hidden 404.

The host is implicitly accepted and may cast one vote without a host invitation. Accepted invitees each have one vote per event. Repeating the same candidate preserves row ID, created_at and updated_at and creates no additional record. Changing candidate updates the same vote row atomically, preserving created_at and recording the current UTC update time. No delete/reinsert or unconstrained upsert is used. There is no vote-withdrawal endpoint.

Example totals:

```json
{
  "data": {
    "totals": [
      {"tmdb_id":550,"movie_night_movie_id":42,"votes":2},
      {"tmdb_id":551,"movie_night_movie_id":43,"votes":0}
    ],
    "my_vote":42,
    "total_votes":2,
    "leaders":[550],
    "voting_open":true
  }
}
```

Every current candidate is included in Core candidate-ID ascending order, including zero counts. `my_vote` is only the caller's selected candidate ID or null. `total_votes` sums authoritative valid votes. Empty shortlists return empty totals/leaders, zero total and null selection. The existing proposed informational `leaders` field is retained: it lists all highest positive-count TMDB IDs in candidate order and is empty without votes. It does not resolve a tie, select/persist a winner or expose a finalization endpoint. No pagination is needed for the existing supported 50-candidate event cap.

## Authorization, privacy and lifecycle

Both routes require host/accepted-only `visibleTo` SQL scoping and `view` authorization. Pending, declined and outsider users, including uninvited administrators, receive hidden 404 without candidate/voting information. The M5.3 minimal-invitation projections remain unchanged. The caller cannot select a voter identity, and the response contains no other participant's selection, vote row ID, voter identity list, private account fields or per-voter timestamps.

Routes reuse `web`, Sanctum sessions, `EnsureAccountAccess`, `EnsureVerifiedAccount`, `PreventAuthCaching` and library-read/write throttles. PUT also uses `EnsureActiveAccount`. Existing Firebase mapping, M7 session-version revocation, CSRF with/without Origin and private/no-store response/error behavior remain intact. Restricted verified host/accepted users may read retained totals but cannot cast/change. Banned/deactivated/unverified/pending-activation accounts cannot use unauthorized workflows. Existing middleware retains 401/403 gates; private policy denial remains hidden 404. No privileged-role bypass exists.

Votes, changes and identical repeats require scheduled state and `now < starts_at`. Exact-start/late/cancelled/finalized mutation attempts by authorized actors return 409. Authorized participants can still read after voting closes with voting_open=false. Supported vote/RSVP/candidate mutations are then closed, so retained totals remain frozen without a separate snapshot table.

Open-state RSVP decline continues to delete the participant's vote atomically through the existing transition. Declined users immediately lose private vote access. Reacceptance restores access, not a vote; a subsequent explicit cast is required. Changing/declining releases the former candidate's vote reference when no other vote remains, while voted candidates retain removal protection.

## Authoritative cohort and aggregate consistency

`MovieNightVote::validFor()` centralizes the approved foundation filter: vote belongs to this event and its voter is the host or a currently accepted invitee. Pending/declined/outsider fixture/invalid votes are excluded. Later account moderation does not retroactively invalidate a previously valid recorded vote; it blocks new actions, preserving the existing approved rule. Internal finalization now invokes this same scope instead of duplicating its filter. Existing winner/tie/state-transition behavior is unchanged; M5.6 remains unimplemented publicly.

Totals acquire actor → **shared parent-event** locks within a three-attempt transaction. Account/private eligibility is checked against the freshly loaded actor/event. The shared parent lock prevents compliant vote, RSVP, candidate, cancellation and finalization mutations from changing the event/candidate set/cohort while reading, while permitting concurrent event readers. One aggregate SQL statement returns candidate vote counts plus caller-specific existence checks; sums/maxima are computed over that bounded result. SQL count is independent of candidate count, tested for two versus ten candidates. This is not a production latency/load benchmark.

No provider metadata is needed. Voting and totals work with missing Catalog credentials and prohibited outbound HTTP; both feature/process tests assert no provider request occurs.

## Mutation transactions, constraints and deadline rechecks

`MovieNightVotingService::cast()` uses `DB::transaction(..., 3)`:

1. Reload/lock actor through `AccountAccess::lock(..., community:true)`.
2. Load/lock the private event exclusively; authorize current private access, scheduled/deadline and existing `vote` permission/current accepted RSVP.
3. Lock the event-scoped candidate, then the caller's existing event vote row if present.
4. Recheck the absolute deadline after these additional lock waits.
5. Associate only server-owned event/voter/candidate IDs and insert once or update a changed selection; identical selection skips save entirely.

Lock order is actor → exclusive event → candidate → caller's vote. The existing unique `(movie_night_id,voting_user_id)` key prevents multiple rows, and the existing same-event composite candidate FK prevents foreign/deleted references. No constraint is weakened. All application mutations share the parent event lock, including M5.4 removal and existing RSVP/cancel/internal-finalize transitions. Candidate removal before a waiting vote produces 404; vote before waiting removal produces 409 and retains the candidate. Failed vote replacement rolls back selection/timestamp together and retains the original row; a forced failure verifies safe generic 500 diagnostics with debug enabled.

New vote paths acquire no target-user lock after the event. The previously reviewed M5.2 host/event/target-user cycle can still interact with actor→event operations; the existing three-attempt Laravel transaction retry remains the recovery mechanism. Exhaustive application-wide deadlock/retry-exhaustion/load testing is not claimed. Direct SQL outside the domain locking/state protocol remains unsupported; database constraints are the final integrity guard, not a substitute for domain authorization.

## Independent-process PostgreSQL coverage

Thirteen cases use committed fixtures, independent PHP/Laravel processes, real row-lock waits observed via `pg_stat_activity`, and controlled release of the lock. Existing services execute opposing mutations in the controlling transaction; none is a new public finalization/voting-identity API.

| Case | Verified outcome |
| --- | --- |
| Same participant, concurrent identical votes | Both complete; one row/selection |
| Same participant, concurrent different first selections | Both complete; one serialized final row |
| Different host/accepted participants | Both complete; two votes, accurate total |
| Competing changes to an existing vote | Same original row survives; final choice is one of the submitted replacements |
| Removal commits before waiting vote resumes | Vote 404, removed candidate has no vote |
| Vote commits before waiting removal resumes | Removal 409, voted candidate retained |
| Decline commits before waiting vote resumes | Vote hidden 404, no vote |
| Vote commits before waiting decline resumes | Decline removes that vote; no residual vote |
| Cancellation commits before waiting vote resumes | Vote 409, no new vote |
| Internal finalization commits before waiting vote resumes | Vote 409, retained host vote/winner unchanged |
| Parent event lock wait crosses real start instant | Vote 409, no vote |
| Candidate row lock wait crosses real start instant | Vote 409, no vote |
| Existing vote row lock wait crosses real start instant | Change 409; old selection/update timestamp preserved |

The last three cases use short real-time waits; others use controlled worker clocks. State/count/selection and host-readable aggregate checks follow worker completion. These are domain-service process tests, not live manual API/browser acceptance. HTTP middleware/contracts are exercised separately by feature tests. Independent tests require the disposable local PostgreSQL guard and exact port 55433 before additive migration/fixture creation; workers independently guard testing mode, local host, `_test` database, empty URL, disposable flag and port. Cleanup removes only their committed fixtures in FK order. Other tests reuse the existing guarded RefreshDatabase harness.
