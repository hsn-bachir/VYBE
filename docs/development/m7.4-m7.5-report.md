# M7.4–M7.5 implementation report — Popular Genres and Activity Analytics

Verified on 2026-11-23 on `feature/m7-genre-activity-analytics`, based on `9a9c8d5` from `dev`. This slice addresses genre popularity and activity under PDF item 11. M7.6 and M7.7 remain open. The working tree contains the implementation for separate Git delivery.

## Behavior and ownership

- **Popular Genres** ranks up to ten genres from the 50 most-watched movies in Core. A movie is ordered by retained watched entries descending, then TMDB ID ascending. Each user/movie row contributes once to every distinct known genre on its movie. Genre ties sort by ascending genre ID. The panel shows the number of movies and watched entries in and outside the cohort through explicit denominators, plus the portion covered by persisted genre metadata. Its bars use the leading genre's count as the scale. Counts can overlap across genres.
- **Genre coverage** uses one authenticated batch lookup of Catalog's persisted `movies.genres` column. Summary-only and missing rows are unknown. A stored empty list is known and contributes zero genre counts. The genre panel shows available results during partial coverage and keeps cohort counts during an outage. The existing reference-candidate response uses empty lists for missing metadata and includes other movie features, so the narrow genre contract preserves the information needed for coverage. The existing summary contract and movie ranking formulas remain intact.
- **Activity Analytics** supports 7, 30 and 90 days. It counts currently retained Core records by `created_at` for registrations, reviews, individual rating records and watched entries. Core includes the current UTC day, fills every missing day with zero, and derives totals from the returned daily rows. Deleted records disappear, rating updates retain their original date, and admin-provisioned account rows count as registrations. Active Contributors counts distinct accounts that created at least one retained review, rating or watched entry. No session activity is collected by these endpoints.
- **Access and delivery** use existing Sanctum, verified-email, live role and account-state checks, and the private administrator read throttle. Verified active and restricted administrators are eligible. Catalog receives only TMDB IDs. The two new Core reads use independent React queries and the Activity Analytics chart supports category buttons, hover and keyboard date inspection, and a native date selector. Deploy Catalog, then Core, then the SPA. There are no schema migrations, indexes, new configuration variables or dependencies.

The [Core API contract](../api/admin-movie-insights.md) and [Catalog batch contract](../api/catalog-batch-summaries.md#catalog-batch-genre-lookup) define the response fields and fallback behavior.

## Performance and coverage

Local Windows HTTP measurements used real Laravel Core and Catalog services with separate disposable PostgreSQL 18 databases and an authenticated Sanctum session. Core contained 5,001 account rows, 15,000 reviews, 75,000 ratings and 120,000 watched entries spread across 240 movies and about 600 days. Catalog contained 240 seeded movie rows with some missing or known-empty genres. The Top 50 group contained 25,189 watched entries. Catalog returned known metadata for 43 of those 50 movies and 21,662 of those 25,189 watched entries. The first read was the first call for its endpoint and range after login. The warm median uses five subsequent calls. Database buffers were already touched by fixture setup.

| Core read | Core SQL¹ | Catalog requests | First HTTP read | Warm HTTP median | Domain SQL execution² |
| --- | ---: | ---: | ---: | ---: | ---: |
| `GET /admin/genre-insights` | 2 | 1 for this cohort, 0 when empty | 684.8 ms | 731.5 ms | 24.63 ms |
| `GET /admin/activity-analytics?range=7` | 2 | 0 | 392.5 ms | 436.1 ms | 36.82 ms |
| `GET /admin/activity-analytics?range=30` | 2 | 0 | 532.0 ms | 416.1 ms | 43.77 ms |
| `GET /admin/activity-analytics?range=90` | 2 | 0 | 391.5 ms | 362.7 ms | 41.69 ms |

¹ Array-backed session/cache measurements include one live account recheck and one domain statement. Persistent session and throttle stores add their configured storage queries. Catalog performs one indexed-ID lookup for a genre batch and no TMDB call.

² `EXPLAIN (ANALYZE, BUFFERS)` measured the SQL separately from HTTP. The genre query scanned watched rows once, hash-aggregated 240 movie groups and used an in-memory top-N sort. Activity grouped dates per table and deduplicated contributor IDs in the same statement snapshot. The measured PostgreSQL 18 plans reused a review visibility/date index, scanned ratings and watches for daily counts and contributor IDs, and kept the contributor sort in memory. At these fixture sizes, the existing schema keeps domain execution below 45 ms. Larger single-table scans and concurrent administrator traffic are the remaining query-plan concerns. Selective windows may benefit from future `created_at` indexes if representative production measurements justify their write and storage costs.
