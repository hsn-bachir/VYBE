# Phase 2D — Firebase administrator identity management

Firebase establishes identity; Core SQL retains role, status, profile, moderation, and audit authority. This extension uses no Firebase custom claims and no new migration. Catalog is unchanged. The legacy administrator routes keep their former behavior when `AUTH_IDENTITY_PROVIDER=legacy`.

## Provisioning and invitation

An active verified admin creates a user or moderator with username and email. Core rejects existing SQL names/addresses and a Firebase UID already mapped to VYBE; it never attaches an unrelated Firebase account by matching email. For a new Firebase email, Core reserves a SQL row and a stable `vybe-invite-...` UID, with a null SQL password and `invitation_pending=true`, then creates a Firebase user with that UID, email, and `emailVerified=false`, **without a password**. For an existing unlinked Firebase email, Core creates an invitation-pending SQL row with no UID until the recipient proves both mailbox access and a fresh sign-in to that exact Firebase identity. It issues the existing SHA-256-hashed, 60-minute one-use invitation token and audits creation only after the relevant Firebase check. Laravel mail sends the invitation. `invitation_delivery=accepted` means transport acceptance; inbox delivery is not proven. The log mailer returns `pending` and never logs the secret link.

The invitation's URL fragment carries the random token to the SPA without sending it to the web server in a GET or a referrer. A recipient with a newly provisioned passwordless identity submits the token and their chosen password to Core. The delivered token is proof of mailbox access. Core sets the Firebase password, marks the Firebase email verified, revokes Firebase refresh tokens, then clears SQL pending state and consumes the token in one SQL transaction. A recipient with an existing Firebase identity signs in with its current password, Google or GitHub method and submits a fresh signed ID token **together with** the invitation token. Core checks the Firebase UID, current email and absence of another SQL mapping, marks the email verified based on mailbox proof if needed, then links the UID and consumes the invitation. It never changes an existing credential or provider. SQL never stores a password. An expired, replaced, or reused token returns the same 422 invitation error. An invited Firebase UID cannot exchange a VYBE session before acceptance.

If Firebase provisioning fails after SQL reservation, the pending row remains. Search for it in Admin Users and use **Resend invitation**; that operation checks the reserved UID and safely retries provisioning, then issues a fresh token. If Firebase succeeded but the SQL invitation/audit write failed, the same resend recovers without creating a second Firebase account. A different Firebase UID owning the reserved email or a UID already mapped to another SQL user is a 409 conflict requiring operator investigation; no automatic identity deletion or email-based merge occurs. If Firebase acceptance succeeds but the SQL transaction fails, the same unexpired invitation can be retried. Do not interpret a 503 as proof that Firebase did nothing.

## Credential and email operations

The Admin User details page requests provider method metadata only for that selected account. The backend checks the live administrator role, then reads the mapped Firebase UID. Password change and reset apply only when Firebase credential metadata reports an existing password. Federated `providerData` entries alone do not establish password eligibility. A Google-only or GitHub-only user receives `PASSWORD_PROVIDER_UNAVAILABLE`; nothing adds a password automatically. Linked password plus Google/GitHub accounts retain their linked methods.

For direct password change and email change, the administrator signs in again through their own password, Google, or GitHub method. Core verifies the signed token's project, revocation, disabled state, recent `auth_time` (default five minutes), and exact match to the admin's SQL-mapped UID. It stores a hash of that token in the configured shared Laravel cache for five minutes so the same confirmation cannot be reused. Configure a shared atomic cache store such as the existing database cache across Core instances. This is separate from the admin's Sanctum session, which remains required with CSRF. Different-UID, stale and replayed tokens fail. Never log or retain the token or password.

Direct password change checks the target UID and password provider, rotates the target's local session version and removes same-database sessions, audits the requested operation, changes the Firebase password, revokes Firebase refresh tokens, then audits completion. If Firebase fails after local revocation, the user may need to sign in again but the credential is not silently reported changed. A post-Firebase SQL/audit failure may leave the credential changed with an incomplete completion record; investigate the requested audit event and Firebase state before retrying. The password-free notification uses the configured Laravel mailer and is best effort.

Password reset initiation asks Firebase to send its own configured email and returns `accepted` only after the SDK accepts the request; inbox receipt is not guaranteed. Existing actor/target throttles remain. Firebase SDK failure returns 503. No Laravel password-broker token is created. For an SSO-only account, explain that the owner must explicitly add a password sign-in method through a secure account management flow; Phase 2D does not implement that optional flow.

Changing an authentication email requires another one-use admin confirmation. Core checks local uniqueness, rotates/removes local sessions and audits the request **before** the remote write. It checks Firebase ownership, updates the same Firebase UID with `emailVerified=false`, then changes SQL email, clears SQL verification, cancels old invitations, and audits completion. The target must verify the new address. Linked OAuth providers remain linked by UID; this operation does not change their provider email or unlink them. If Firebase succeeds and SQL fails, an authorized repeat with a new admin confirmation detects that Firebase already has the requested email and completes SQL reconciliation. A competing email owner or unrecognized Firebase email requires operator investigation. The last verified active administrator cannot change their own email.

## Browser acceptance

1. Configure Firebase Admin credentials and matching frontend Firebase project; use a working mail transport (`MAIL_MAILER=log` cannot deliver invitations). Confirm password, Google and GitHub providers are enabled in Firebase.
2. Sign in as a mapped, verified active admin. Create a user and a moderator. Confirm each has a stable numeric SQL ID, pending invitation, null SQL password, and unverified Firebase identity with the same UID.
3. Open a newly provisioned identity's invitation. Set a password, confirm one-use acceptance, sign in, and verify the original SQL ID and role. Invite a person who already owns an unmapped Firebase identity; sign in through its current method during acceptance and verify the same UID is linked without a new password. Try expired/reused links and a delivery failure; check the UI does not report delivery for pending mail.
4. On a password account, send a reset. Confirm Firebase's email arrives and the password reset flow works. Try a Google-only and GitHub-only account; reset and direct change must be unavailable without adding a password.
5. Choose direct password change. Reauthenticate as the administrator with password, Google, then GitHub on separate attempts. Confirm the changed password works, the old one fails, previous VYBE sessions are rejected, and the confirmation cannot be replayed or used with another UID.
6. Edit a target email. Confirm fresh admin authentication, Firebase and SQL show the new address on the same UID, verification is cleared, and old sessions are rejected. Check a SQL collision, Firebase collision, and a linked Google/password account.
7. Confirm ordinary user and moderator sessions cannot call admin identity routes. Confirm a banned/deactivated admin cannot write. Ban and restore a target; Firebase identity must remain enabled and SQL restrictions still apply.

Automated tests mock Firebase. Live OAuth popup, email transport, multi-browser session, and partial network failure acceptance remain release gates.
