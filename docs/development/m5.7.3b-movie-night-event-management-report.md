## Implementation and design decisions

- Replaced creation/detail placeholders with lazy real pages under the existing protected routes. Creation enforces active/verified account permission even on direct navigation; its Cancel action returns to the dashboard. Successful creation navigates using the server-returned ID, rechecking the current access boundary before navigation.
- One reusable form serves creation and the organizer edit dialog: title, date/time, searchable native IANA datalist with browser suggestion, optional location/HTTPS meeting URL, selected-zone schedule preview, explicit overlap choices and save/cancel controls. Native date/time inputs support seconds. Zone changes preserve wall time and reset any overlap choice. Existing dateTime utilities reject DST gaps and produce strict UTC seconds; edit initialization round-trips the saved UTC instant, including a known earlier/later overlap occurrence.
- Constraints mirror Core: nonblank title ≤150 Unicode characters; strict UTC start after now; valid IANA timezone ≤64; nullable location ≤500; nullable HTTPS URL ≤2048. Character checks count Unicode code points rather than imposing stricter HTML UTF-16 `maxLength` limits. No date/year/runtime/location constraints or dependencies were invented. Backend validation remains authoritative, and recoverable validation/service/session-bootstrap failures preserve input values.
- Edits send only changed fields, with explicit null for cleared optional values. Empty PATCH is prevented. A synchronous submission guard plus disabled fieldset prevents repeated create/edit submission; cancellation has an equivalent guard. Every write still uses the approved CSRF adapter and disabled mutation retry policy.
- Private details display authoritative title/organizer/status/schedule/location/link/relationship. Meeting URLs are HTTPS-only, protected against opener access and rendered as text safely. Participants, Shared shortlist and Voting are visibly separate future sections without counts, data requests, actions or invented results. No winner is calculated or inferred.
- Organizer actions follow existing permissions. A shared native Dialog supplies modality, focus containment, Escape handling, busy-state dismissal prevention and focus restoration. The edit title input and safe Keep movie night confirmation action receive explicit initial focus. Cancellation explains irreversibility/history retention, applies the full server response immediately, refreshes affected summary/totals queries and removes management actions after closure.
- Layout reuses dashboard colors/semantic tokens, typography, Avatar, Input, Button, MovieState and Dialog. Creation has a form/aside on larger screens and one column on smaller screens; details and future sections remain in normal flow; edit/confirmation dialogs scroll internally. No shared styling/auth implementation or unrelated feature was redesigned.

## Authorization, privacy and stale state

Only valid canonical positive IDs exactly representable by the existing numeric DTO enter detail queries. Invalid IDs cause no request. Core remains responsible for checking host/accepted membership: pending, declined and outsider direct navigation receives the same generic unavailable state. Restricted verified accounts retain authorized detail reads but no creation/edit/cancellation controls; terminal events are read-only. If runtime timezone data is unavailable, details remain readable and editing is withheld rather than initializing an incorrect schedule.

The approved query/mutation adapters and account-scoped cache remain in use. Authoritative edits now use the same read-revision/cancellation mechanism as terminal lifecycle updates, preventing older detail/list/inbox reads from overwriting the returned event. Writes for unrelated events are not revoked. Overlapping edits or intervening detail updates are reconciled through an authorized GET rather than ordered by timestamps, dispatch or arrival; terminal cache state cannot revert to scheduled. A returned terminal transition takes precedence over a scheduled cache even when server timestamp ordering is skewed. Cancellation continues using the approved lifecycle helper.

A feature-local access-version subscription exposes session/owner/event revocation to mounted form boundaries via useSyncExternalStore. These boundaries are keyed by owner, verification and route ID; logout, account switch, denied access and known account-wide revocation unmount the affected form/dialog. Restriction also unmounts mutation forms via permissions. Only editable values/baselines/errors are kept in component state; the private Event itself is not copied into independent state or storage. Unrelated event revocation preserves the current form. Query/mutation cache/observer cleanup remains active.

A deadline timer, bounded for browser timer limits and refreshed on focus/visibility, recomputes permission hints at the original start. Editing closes while scheduled-host cancellation remains available. Client time is advisory; Core rechecks account, lifecycle and deadlines under its existing locks. No authentication implementation, backend/API/schema/config/environment/lockfile/dependency changes or migrations.

### Dialog permission restoration

**Root cause:** gating dialog rendering by permissions unmounted its form but retained the parent `dialog` selection. A later permission restoration could therefore reopen it automatically. The detail component now computes permission/display gates before its early returns and conditionally clears its own selection during render when that selection loses permission. This is a guarded adjustment of local selection state, not a side effect of refetch or a deferred effect: the revoked dialog/draft is removed before commit, and restoration never sets a selection. A fresh click initializes the form from the current authoritative Event.

The management browser suite now keeps the actual page mounted for eight edit/cancel scenarios covering restriction, deadline, lifecycle projection changes and event-access revocation. It verifies no retained draft or automatic reopening, fresh authoritative edit values after an explicit reopen, and cleared cancellation errors. Deadline expiry correctly closes edit while preserving scheduled-host cancellation permission; the cancellation deadline case confirms that distinction. A revoked access boundary remains unavailable on server-side restoration until explicit navigation establishes a fresh authorized read. Synthetic terminal-to-scheduled fixture restoration tests the client against a corrected projection; it does not add a product reopen operation or change the backend lifecycle contract.

### Equal-timestamp competing edit responses

**Root cause:** `updated_at` equality could allow an older successful response to replace a newer event solely because it arrived last. A server timestamp is not an event version or a reliable ordering token.

Each edit now has a feature-local attempt record scoped to QueryClient/session owner/event. It records only query hashes/update counters, contention and cleanup, with no private Event copies. Overlap marks all participating attempts as ambiguous; it does not rank them. A detail update occurring after dispatch also makes a response ambiguous. Uncontended edits with an unchanged detail baseline still apply their server-returned Event immediately, including same-timestamp writes. Ambiguous responses leave current cache data untouched and invalidate/refetch the existing authorized detail query, including inactive cached details. Calls without dispatch provenance also reconcile instead of assuming timestamp ordering.

Every ambiguous success advances the existing read generation and cancels older reads before refetch. A delayed competing response causes another authorized reconciliation, so its older payload cannot overwrite the result or revive a superseded GET. Terminal lifecycle updates retain immediate priority and scheduled responses cannot reopen terminal data. Attempt records are released in `finally`, including validation/transport failures. No sequence number is sent to Core and no timestamp, client dispatch order or response arrival order is treated as authoritative. Confirmed writes retain successful mutation outcomes if reconciliation fails; the read failure remains a retryable query error, without automatic write retries. Session/event revocation and unrelated event operations retain their previous isolation.

The 13 added unit cases test both arrival orders and both possible server-final values with identical timestamps, uncontended same-timestamp edits, intervening detail refreshes, delayed uncancellable reconciliation reads, revocation/account switching, terminal protection, reconciliation error/retry, failed-attempt cleanup, and unrelated event request/write isolation. Both mocked browser suites passed again: 9 management groups (20 responsive checks plus the eight mounted restoration cases) and 12 dashboard groups (8 responsive checks), with no page errors. All HTTP and writes remain fixture-only. Final exact command results appear in the verification table above; lint has no warnings.

The correction adds a bounded authoritative detail read after ambiguous successes. While that read is pending the prior authorized detail may remain visible; a failure shows the existing query error/retry state. Live server concurrency and other devices changing data after reconciliation remain separate acceptance work; no server revision token or realtime transport was introduced.
